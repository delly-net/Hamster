# Hamster UI

仓鼠理财管家的前端工程：Vue 3 + TypeScript + Vite。

## 技术栈

| 项 | 选型 |
|---|---|
| 框架 | Vue 3.5（组合式 API，`<script setup>`） |
| 语言 | TypeScript 6.0（`vue-tsc` 做类型检查） |
| 构建 | Vite 8 |
| 路由 | Vue Router 5 |
| 状态管理 | Pinia 4 |
| 代码质量 | ESLint 10 + oxlint + Prettier |
| 包管理 | pnpm（唯一锁文件 `pnpm-lock.yaml`） |
| 开发端口 | 5173 |

## 品牌资源与配色

### 品牌资源

产品视觉资产来自仓库根目录的 [`doc/`](../doc)，落地到本工程的映射：

| 源文件 | 目标 | 用途 |
|---|---|---|
| `doc/Hamster.ico` | [`public/favicon.ico`](public/favicon.ico) | 站点图标（`index.html` 的 `rel="icon"` 已引用该路径，替换文件即生效） |
| `doc/Hamster_512.png` | [`src/assets/logo.png`](src/assets/logo.png) | 全站主 Logo（完整头部 34px、登录页卡片内 56px） |

`logo.png` 是 512×512 的**带透明圆角位图**，可干净地落在渐变页底上，无需再加底板。更换品牌图只需覆盖这两个文件——它们取代了脚手架自带的 Vite 图标与 Vite `logo.svg`（后者已删除）。

### 配色令牌

配色取自 Logo 本身（琥珀橙底、条纹焦糖橙、腹部奶油、深暖棕描边），全部集中在 [`src/assets/base.css`](src/assets/base.css)。**页面样式一律引用语义令牌，不再出现硬编码色值**：

| 令牌 | 亮色 | 暗色 | 用途 |
|---|---|---|---|
| `--color-accent` | `#e8934a` | `#f0a85c` | 主色：按钮实底、聚焦环、链接、选中态边框 |
| `--color-accent-strong` | `#d97b2e` | `#f7bc7c` | 主色加深：hover、小字号彩色文本 |
| `--color-accent-soft` | `rgba(232,147,74,.14)` | `rgba(240,168,92,.18)` | 主色浅底：hover 填充、选中态背景 |
| `--color-accent-contrast` | `#ffffff` | `#2a1b0e` | 主色实底上的前景色（**暗色下翻转为深棕**） |
| `--color-danger` / `-soft` / `-border` | 砖红系 | 暖珊瑚系 | 表单与请求报错 |
| `--gradient-page` | 奶油三档渐变 | 深棕三档渐变 | `body` 页底（`background-image`，`background-color` 兜底） |
| `--radius-card` / `--radius-control` | `18px` / `10px` | 同左 | 卡片与控件的圆角 |
| `--shadow-card` / `--shadow-control` | 暖棕柔和投影 | 纯黑投影 | 卡片浮起与控件层次 |

设计约定：

- **换肤只改 `base.css` 一处**——强调色收敛为上述三件套后，全站再无硬编码品牌色（先前 12 处散落的 Vite 绿已全部替换）。
- **暗色分支必须重新声明 `--gradient-page`**，否则暗色下会残留亮色奶油渐变（`prefers-color-scheme` 只覆盖显式列出的变量）。
- **`--color-accent-contrast` 在暗色下翻转**：暗色主色是亮橙，白字对比度不足，须配深棕文字。
- `/openapi` 页的**HTTP 方法徽标**（GET 蓝 / POST 绿 / PATCH 橙 / DELETE 紫等）刻意保留各自语义色，不并入品牌色，以维持方法间的可辨识度。

## 页面布局

全站为经典的「header + body」后台结构：

```
┌──────────────────────────────────────────────────┐
│ header：产品 Logo + 产品名 │ 用户名 · 账套 + 切换 · 退出登录 │ ← 账号区仅宽屏
├──────────────┬───────────────────────────────────┤
│ body 左侧     │ body 右侧                          │
│ 功能菜单侧栏   │ 内容主体区（路由页面）                │
└──────────────┴───────────────────────────────────┘
```

窄屏（<1024px）下侧栏收成抽屉，header 只留品牌，**账号区落到抽屉底部**（分割线以下）：

```
┌──────────────┐
│ 功能菜单项…    │
│ ─────────────│ ← 分割线
│ 用户名         │
│ 账套名 + 切换  │  ← 吸底（margin-top: auto）
│ [ 退出登录 ]   │
└──────────────┘
```

| 环节 | 实现 |
|---|---|
| 骨架 | [`src/App.vue`](src/App.vue) 渲染 `header.app-header` + `div.app-body`（`aside.app-sidebar` 菜单 + `main.app-main` 内容区） |
| header 左侧 | 汉堡按钮（仅窄屏）+ 产品 Logo（34px）+ 产品名「仓鼠理财管家」 |
| header 右侧 | **仅宽屏**。已登录时依次为**用户名 → 当前账套名 +【切换】→【退出登录】**；未登录时仅显示「登录 / 注册」入口 |
| 功能菜单 | 数据源为 [`src/config/menu.ts`](src/config/menu.ts)，以**路由名**指向路由；`adminOnly: true` 的项（接口调试、用户管理、账套管理、币种管理）仅管理员渲染；「首页」「收入」「支出」「转账」「账户管理」「分类管理」「标签管理」「账目明细」与末尾的「用户设置」面向所有登录用户。记账是最高频的日常动作，故「收入」「支出」「转账」三个入口紧随首页；「分类管理」「标签管理」与「账户管理」同属记账的基础字典，故紧随其后 |
| 滚动模型 | `main.css` 把非空白布局的 `#app` 锁为整屏高度 + `overflow: hidden`，滚动交给 `.app-main`；header 与侧栏因此保持不动 |
| 内容区宽度 | 页面**铺满** `.app-main` 的可用宽度，内边距统一由 `.app-main` 提供，页面自身不再限宽居中 |
| 窄屏（<1024px） | 侧栏收起为抽屉，由 header 内汉堡按钮开合；路由跳转 / `Esc` / 点击遮罩均可关闭 |
| 窄屏账号区 | header 右侧的 `.account` 整块隐藏，改由抽屉底部的 `.drawer-account` 呈现（用户名 → 账套名 +【切换】→【退出登录】，未登录时为「登录 / 注册」）——**同一份信息的双呈现**，两处模板结构与类名一一对应，增删字段必须同时修改。上边框即「功能菜单 ｜ 账号区」两段之间的**唯一一条分割线**；`margin-top: auto` 使其在抽屉内吸底，菜单变长也随之滚动 |
| 空白布局例外 | 路由标 `meta: { layout: 'blank' }`（登录页、重置密码页）时不渲染 header 与侧栏，仅页面内容 + 一行版权页脚 |

新增功能菜单项只需在 `src/config/menu.ts` 的 `menuItems` 中追加一项（`routeName` 对应路由 `name`），`App.vue` 无需改动。

## 运行时配置

后端地址不再硬编码在源码中，而是由 [`public/conf/setting.json`](public/conf/setting.json) 提供，应用启动时通过 `fetch` 读取：

```json
{
  "api": {
    "baseUrl": "http://localhost:5004",
    "openApiDocPath": "/openapi/v1.json",
    "timeoutMs": 15000
  }
}
```

| 字段 | 说明 |
|---|---|
| `api.baseUrl` | 后端服务基址（末尾斜杠可省略） |
| `api.openApiDocPath` | OpenAPI 文档路径，相对 `baseUrl` |
| `api.timeoutMs` | 文档拉取与调试请求的超时时间（毫秒） |

`public/` 下的文件会被原样拷贝到构建产物，因此**部署后可直接修改该文件调整后端地址，无需重新构建**。文件缺失或字段缺省时回退到内置默认值（同样是 `http://localhost:5004`），不会阻断启动。

## 接口调试页 `/openapi`

开发时访问 `http://localhost:5173/openapi`，页面会读取上述配置中的 OpenAPI 文档并渲染：

- **左侧**：按 Tag 分组的接口清单，支持按路径 / 摘要 / operationId 搜索；
- **右侧**：选中接口的详情与调试面板——按位置（path / query / header）填写参数、编辑 JSON 请求体（默认按 schema 推导出示例骨架）、点击「发送请求」查看响应状态码、耗时、响应头与响应体（JSON 自动美化，可一键复制）。

注意事项：

- **入口仅系统管理员可见**：左侧功能菜单的「接口调试」项标了 `adminOnly: true`，普通用户与未登录访客看不到它。但该页是开发调试工具，**路由本身未加守卫、依然公开**——直达 `/openapi` 对任何访客可用，别把它当成受保护页面；
- 该文档**仅在 Development 环境由后端暴露**，后端以其他环境启动时 `/openapi/v1.json` 返回 404，页面会给出对应提示而不是白屏；
- 调试请求直接发往 `api.baseUrl`，本地联调依赖后端已放行的 CORS（见下节）；
- 请求体编辑目前仅支持 `application/json`。

## 登录与注册 `/login`

以「用户名 + 密码」登录，登录态由后端签发的 JWT 承载。页面为登录 / 注册合一的表单（Tab 切换）：

- **注册**：用户名 3–32 位字母、数字或下划线，密码至少 6 位；用户名全局唯一（查重不区分大小写）。注册**不会自动登录**——新账号默认未激活，注册成功后页面**切回登录 Tab** 并提示「注册成功，请等待管理员激活后登录」，同时清空密码框。按钮文案相应为「注册」而非「注册并登录」。
- **登录**：凭据错误时提示「用户名或密码错误」（后端不区分用户不存在与密码错误，避免枚举用户名）；账号未激活时提示「账号尚未激活，请联系管理员激活」，且**不写入令牌**、不跳转，用户可原地重试。

### 空白布局

登录页为**空白布局**（见「页面布局」）——未登录用户不应看到应用内的功能菜单与其他模块入口，故该页不渲染 header 与侧栏，卡片外仅保留一行版权页脚，表单卡片在视口内水平垂直居中。品牌 Logo 由登录页自身承载，**位于表单卡片内部顶部并居中**（56px），与标题、Tab、表单构成同一视觉整体。

| 环节 | 实现 |
|---|---|
| 布局声明 | 路由上标 `meta: { layout: 'blank' }`（见 [`src/router/index.ts`](src/router/index.ts)） |
| 头部/菜单/页脚切换 | [`src/App.vue`](src/App.vue) 依 `route.meta.layout` 在空白布局下只渲染页面与版权页脚，同时在 `body` 上切换 `layout-blank` 类 |
| 版式分支 | [`src/assets/main.css`](src/assets/main.css) 的 `body:not(.layout-blank) #app` 只在完整布局下锁定整屏高度；卡片的居中由页面自己用 `margin: auto` 完成 |

其余路由（`/`、`/settings`、`/openapi`、`/admin/*`）沿用完整 header-body 布局。新增其它空白页只需在路由上补 `meta: { layout: 'blank' }`，无需改动 `App.vue`。

### 登录态的存放与恢复

| 环节 | 实现 |
|---|---|
| 令牌存放 | `localStorage`（键 `hamster.auth.token`），隐私模式等不可用时降级为内存存储 |
| 令牌附加 | [`src/api/http.ts`](src/api/http.ts) 自动附加 `Authorization: Bearer <token>` |
| 启动恢复 | `main.ts` 在安装路由前调用 `auth.restore()`，凭本地令牌请求 `/api/auth/me` 还原用户；失败则静默登出 |
| 令牌失效 | 请求返回 401 时统一清空令牌并跳转登录页——登录 / 注册接口自身的 401 例外（传 `handleUnauthorized: false`），避免把「密码错误」误判为登录失效 |

令牌有效期**固定 1 天**，过期或后端更换签名密钥后需重新登录。

## 用户管理 `/admin/users`

系统管理员专用的用户管理台（[`src/views/UserAdminView.vue`](src/views/UserAdminView.vue) + [`src/stores/users.ts`](src/stores/users.ts)），列表展示序号、用户名、角色、激活状态与注册时间，并提供三类操作：

| 操作 | 行为 |
|---|---|
| 激活 / 停用 | 双向开关。停用后该用户无法再登录；**已签发的令牌在过期前仍可用**（见下方「已知边界」） |
| 重置链接 | 生成有效期 15 分钟、一次性的专属链接，页内展示全文并提供一键复制；重新生成会使旧链接立即失效 |
| 删除 | 需二次确认（按钮就地变为「确认删除 / 取消」，不使用 `window.confirm`，以免阻塞无头渲染与自动化）；删除后该用户令牌立即失效，用户名可被重新注册 |

设计约定：

- **入口显隐只是体验**：左侧功能菜单的「用户管理」入口按 `auth.isAdmin` 显隐，路由守卫也会挡回非管理员，但**真正的防线是后端**——每个管理端点都回查数据库确认调用者仍是启用状态的管理员。篡改前端状态只会看到一个请求全部失败的页面。
- **自锁保护**：当前登录账号所在行标「当前账号」，其「停用」「删除」按钮置灰；后端对同一规则有独立校验，绕过前端只会得到 400。
- **序号列是行号不是 Id**：取 `v-for` 的行下标 +1，按当前列表顺序连续编号，刷新后重算。**不要改成 `user.id`**——删过用户就会出现断号，容易被误读为数据缺失。
- **时间显示**：后端回传的是带 `Z` 的 UTC 时间，页面用 `Intl.DateTimeFormat` 按浏览器本地时区渲染。
- **本页成功提示复用主色**：管理台的确认提示不属于收/支/转账任何一种语义（那三色只用在记账页，见「收入 / 支出 / 转账」小节），故沿用品牌主色。

> **已知边界**：停用只阻止**新的登录**，已签发的令牌在其 1 天有效期内仍可访问非管理接口。若需要「停用即踢下线」，需在服务端的令牌校验环节回查用户状态（本项目当前未实现）。

## 账户管理 `/accounts`

面向**所有登录用户**的记账账户管理页（[`src/views/AccountView.vue`](src/views/AccountView.vue) + [`src/stores/accounts.ts`](src/stores/accounts.ts)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。页面**按账户类型分页签**呈现列表，**新建与修改统一走弹窗**（【新增】/【编辑】→ 表单 →【保存】落表），并支持停用/启用。

| 环节 | 行为 |
|---|---|
| 未选择账套 | 只显示「请先切换账套」的提示，**不渲染页签、弹窗与表格**——账户一律挂在账套下，展示一个不属于任何账套的空列表只会误导 |
| 跟随账套切换 | `watch` 账套 store 的 `currentId`，变化即重新拉取；未选择时清空列表。**仅靠 `onMounted` 会残留上一账套的账户**；账套一变也顺手关掉**两个**弹窗，否则弹窗里留着的是上一个账套的填写内容。页签是视图偏好而非账套数据，**换账套后保持不动** |
| 页签切换 | 页签即账户类型（资金 / 负债 / 往来，默认停在**资金账户**），集合与顺序直接取自 `ACCOUNT_TYPE_OPTIONS`。切换**不重新请求后端**——列表接口一次就返回当前账套内我可见的全部类型，换页签只是换一个 `computed`；序号按当前页签的列表从 1 重排，空态文案带上类型标签 |
| 页签键盘操作 | `role="tablist"` / `role="tab"` / `role="tabpanel"` + roving tabindex：`Tab` 只落在活动页签上，`←` `→` 循环移动、`Home` `End` 跳首尾，移动即切换并把焦点交给新页签 |
| 新建（弹窗） | 点【新增】弹出表单（【保存】落表、【取消】/`Esc`/点遮罩关闭），字段为名称 + 归属范围（个人/公共）+ 类型（**三选一**）+ 期初金额 + **期初时间**。**类型默认取当前页签**；用户若改选为别的类型，保存成功后**自动切到该类型页签**，否则新建的账户不在当前列表里，会让人以为没建成功而重复提交。归属人由后端强制为当前登录者，故表单**没有**归属人字段。期初金额非 0 时后端会同时落成一笔期初交易，期初时间即那笔交易的业务时间。每次打开都复位表单；**提交中禁止关闭**（请求已发出，此刻关掉会让人以为没建成功而重试） |
| 期初时间（新建时选） | `<input type="datetime-local">`，默认**当前本地时间**，提交前经 `toUtcIso()` 转 UTC ISO（与记账页「发生时间」同一控件、同一口径）。晚于当前时间**超过 5 分钟容差**时前端先拦住、后端同样返回 400（`errors.openingAt`）——容差是因为本机与服务器时钟必有偏差，严格判定会让「默认值直接提交」偶发失败。期初金额为 0 时不写期初分录，该值也随之无落点 |
| 修改（弹窗） | **只可改名称**；账户类型、归属范围、期初金额均**不可改**（类型是账户的分类身份，归属范围个人 → 公共等于把私有数据公开给全账套，期初金额已落成一笔期初交易），故弹窗内以**只读文本**呈现归属范围、类型、期初金额与余额，不提供这三者的可编辑控件。与新建弹窗同规则：打开即聚焦、`Esc` / 点遮罩 /【取消】关闭、提交中禁止关闭 |
| 停用 / 启用 | 停用需二次确认（就地变为「确认停用 / 取消」），启用直接生效；按钮文案统一用「停用」而非「删除」，与后端软删除语义一致 |
| 显示已停用 | 勾选框驱动列表请求的 `includeInactive`，勾选即重拉，无需手动刷新；它是**全局**开关，与页签叠加生效 |
| 金额呈现 | `Intl.NumberFormat` 固定两位小数，右对齐 + `tabular-nums` 便于纵向比对 |
| 窄屏呈现（<1024px） | 表格隐藏，当前页签的账户改为**卡片流**（`ul.cards`，一个账户一张卡）：卡片头部左侧是账户名 + 状态徽标、右侧是**余额**（视觉主位，主色加粗、等宽），其下依次是「归属范围 + 归属人 · 币种 · 期初金额 · 创建时间」与底部的**操作区**；空态与宽屏**逐字相同**（同一条件、同一文案表达式） |

设计约定：

- **个人账户的「私有」由后端维持**：列表里看不到他人个人账户、直接构造请求改他人个人账户返回 404，都是后端判定的结果。本页**不做任何本地过滤**——前端的可见性只是体验层，篡改本地状态只会拿到一批 403 / 404。
- **页签是纯呈现层的分组，不是「本地过滤」**：上面那条约定针对的是**可见性/权限**（前端过滤只会造出假防线），而按类型分页签是**展示分组**，后端返回的数据一行都没被丢掉。也正因为列表已含全部类型，**页签切换不该触发重新请求**。若将来要给列表加按类型查询的参数，要先想清楚是否值得把展示需求扩散成接口变更。
- **类型下拉只有三项（没有账本账户）**：账本账户由系统在期初入账时自动创建，后端既不返回它（列表与单条查询都过滤）、也拒绝手工新建（`POST` 传 `Ledger` 一律 400），故本页既看不到它也无法造出它，**无需为此写任何本地过滤或禁用逻辑**。**页签也只有三个也正是这个原因**——能呈现的类型只有三类。`ACCOUNT_TYPE_OPTIONS` 与 `ACCOUNT_TYPE_LABELS` 分工不同：前者是「用户可选什么」（三项），后者是「接口可能回传什么」（后端枚举的完整镜像，故仍含 `Ledger`），**少一项不是遗漏**。
- **账户类型不可修改**：类型是账户的分类身份，既有流水都按它归类，换类型等于给历史流水换一套解释，故修改弹窗里只读呈现、不提供控件（**连禁用的下拉也不给**——禁用控件仍会暗示「以后能改」）。后端 `PUT` 的请求体同样只有 `name`，带上 `type` 也不会被读取。这条限制还顺带消灭了「先建资金账户再改成账本账户」的绕过路径，后端因此不再需要在该端点上做类型校验。
- **不可修改的字段一律只读呈现**：本页对「一经创建不可修改」的字段（类型、归属范围、期初金额、期初时间）不呈现任何可编辑或禁用的控件。表格里因此**没有「类型」列**——页签已把类型钉死在整表唯一值上，那一列每个单元格都是同一个标签，属纯冗余；类型信息并未丢失，修改弹窗里仍以只读上下文呈现，页签标题本身也在陈述。
- **期初时间只在新建时可选，且本页不呈现**：它是「这笔期初余额是**什么时候**的余额」，由后端直接落成那笔期初交易的 `occurredAt`。账户表**刻意不存这一列**——期初时间已经活在期初分录上，另立一列就是同一事实两处存储，与「余额不落库」是同一条理由。因此本页的宽屏表格与窄屏卡片**都不呈现它**：它的可见处是账目明细页的那条期初行。代价是期初金额为 0 时时初时间一并丢弃（零额期初连同时刻都不含信息，与「零额不写分录」同一取舍）。
- **修改弹窗的只读上下文是打开时的快照**：它取自 `editTarget` 指向的那个账户对象。唯一能改动账户的操作是保存成功，而成功即关窗，故快照不会有机会变成陈旧显示，不必为此加额外的重新拉取。
- **两个弹窗的错峰呈现**：页面级错误提示只在**两个弹窗都关闭**时渲染——弹窗打开时页面级提示会被遮罩盖住，用户看不到，错误必须呈现在弹窗内。
- **余额是派生值**：页面展示的余额来自后端的 `balance` 字段（该账户全部交易明细的有符号汇总，期初已计入其中）。**不要在前端用期初金额渲染余额列**，那会在有流水之后与后端脱节。
- **期初金额只读**：它已落成一笔期初交易，改写它等于篡改既成事实，故 `UpdateAccountPayload` 不含该字段，修改弹窗里也只读呈现。`UpdateAccountPayload` **只剩 `name`**：归属范围、归属人、期初金额与类型全部不可修改，后端 `AccountUpdateRequest` 与之一一对应。
- **序号列是行号不是 Id**：同用户管理页，取行下标 +1，停用账户后不会断号；**按当前页签的列表计数**，切换页签后从 1 重新开始。
- **未选账套时的 400 是预期行为**：后端对不带 `X-Account-Set-Id` 的请求返回 400「请先选择账套」，这正是页面在无账套时不发请求的原因。
- **窄屏卡片流与宽屏表格是同一份数据的双呈现，用 `display` 切换**：两份 DOM 始终并存，由本站**唯一**的 1023px 断点（定义在 [`src/App.vue`](src/App.vue)）决定谁可见。页面级适配**不得自建断点或改用 JS `matchMedia`**——两个断点一旦错开，就会出现「表格与卡片同时可见 / 同时不可见」的窗口。这里的 `display: none` 与「隐藏同一份内容里的冗余字段」不是一回事：那类隐藏（如本页不呈现类型列）删掉也不影响信息完整性，属死代码；这里是**某一时刻整份呈现都不适用**，隐藏是它的定义。前提是「任一时刻恰有一份进入无障碍树」，故两份呈现不能同时可见。
- **卡片里余额是主位、期初金额降为次要标注，两者缺一不可**：这与账目明细卡片「三个金额只留一个」的口径不同——明细单行上净额恒等于收入或支出之一，而**期初金额与余额只在账户还没有任何流水时才相等**，是两个独立信息，省掉期初等于窄屏丢一个字段。故余额（当前家底）占卡片头部右侧、复用宽屏 `.balance` 的主色加粗；期初金额与归属、币种、创建时间同处次要行。
- **卡片底部保留完整操作区，一个按钮都不能少**：宽屏的表格在窄屏是**整块隐藏**的，卡片底部就是手机上唯一的管理入口，故编辑 / 停用 / 启用 / 确认停用 / 取消全部平铺，二次确认同样是就地切换（不改成 `window.confirm`）。卡片内的按钮只在断点内放大到触控友好尺寸（`min-height: 2.25rem` + 13px 字号），宽屏按钮尺寸逐字不变。
- **卡片不呈现序号**：与账目明细同一口径——序号只是表格里的行计数，本页的序号还只是「按当前页签从 1 重排」的行号，摆在卡片里更容易被误读为账户编号。
- **窄屏菜单的「自动识别」是布局层的事，本页不参与**：侧栏收成抽屉、按 `router-link-active` 高亮当前页、路由跳转后自动收起，均由 [`src/App.vue`](src/App.vue) 的 1023px 断点与 `watch(route.fullPath)` 统一提供，新增页面**天然获得**，不需要（也不应该）在页面里写任何菜单相关逻辑。

## 分类管理 `/categories`

面向**所有登录用户**的记账分类管理页（[`src/views/CategoryView.vue`](src/views/CategoryView.vue) + [`src/stores/categories.ts`](src/stores/categories.ts) + [`src/components/CategorySearchSelect.vue`](src/components/CategorySearchSelect.vue)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。分类是**账套内所有成员共用的字典**（与账户同属记账的基础字典），且记账时手工输入即会自动建分类，把维护收进管理端毫无道理。页面**新建与修改统一走弹窗**（【新增】/【编辑】→ 表单 →【保存】落表），并支持停用/启用。

设计约定：

- **分类不区分收入 / 支出 / 转账，故本页没有类型页签、也没有类型筛选**：分类是「钱花在什么事上」，资金流向已由交易类型承载。给分类绑类型会逼着同一个名字按类型各建一份，而同一个分类本就可能既用于收入又用于支出（如购物退款）。
- **所属账套不可修改**：改账套等于把一份分类从一本账搬到另一本，挂在该分类上的历史明细会跟着换一套解释；后端 `PUT` 的请求体同样只有 `name`，带上账套也不会被读取。
- **表格里没有「账套」列**：整表都在当前账套内，那一列每个单元格都是同一个名称，属纯冗余；账套信息并未丢失，修改弹窗里仍以只读上下文呈现。
- **不播种，空字典是正常起点**：后端不预置任何分类（各家的业务语义不同，「所有人都需要的那几个」不存在共识，且播种后用户删掉的分类会在重启时被塞回来）。故首次进入本页看到空表是预期现象，**空态文案要指向「去记账时直接输入新分类名即可自动创建」**，而不是让人以为功能坏了。这也正是下面那条「与账户页的差异」的由来。
- **与账户页的最大差异：本页的「新增」不是唯一入口**：记账页手工输入一个不存在的分类名，后端会自动创建它。故本页不是「不建分类就没得选」，而是「建好之后记账时可以筛、可以点选」。
- **不做任何本地过滤**：分类**没有可见性维度**——账套内每个分类对每个成员都可见（这一点与账户不同，账户分公共/个人）。前端篡改本地状态只会拿到 403 / 404。
- **序号列是行号不是 Id**：同账户管理页，取行下标 +1，停用分类后不会断号。
- **停用分类仍在明细里显示名称（不在本页）**：本页只管字典本身；历史明细上停用分类的名称照常呈现，见「账目明细」一节。
- **未选账套时的 400 是预期行为**：后端对不带 `X-Account-Set-Id` 的请求返回 400「请先选择账套」，这正是页面在无账套时不发请求的原因。
- **窄屏卡片流与宽屏表格是同一份数据的双呈现，用 `display` 切换**：两份 DOM 始终并存，由本站**唯一**的 1023px 断点（定义在 [`src/App.vue`](src/App.vue)）决定谁可见。页面级适配**不得自建断点或改用 JS `matchMedia`**——两个断点一旦错开，就会出现「表格与卡片同时可见 / 同时不可见」的窗口。这里的 `display: none` 与「隐藏同一份内容里的冗余字段」不是一回事：那类隐藏删掉也不影响信息完整性，属死代码；这里是**某一时刻整份呈现都不适用**，隐藏是它的定义。前提是「任一时刻恰有一份进入无障碍树」，故两份呈现不能同时可见。
- **卡片底部保留完整操作区，一个按钮都不能少**：宽屏的表格在窄屏是**整块隐藏**的，卡片底部就是手机上唯一的管理入口，故编辑 / 停用 / 启用 / 确认停用 / 取消全部平铺，二次确认同样是就地切换（不改成 `window.confirm`）。卡片内的按钮只在断点内放大到触控友好尺寸（`min-height: 2.25rem` + 13px 字号），宽屏按钮尺寸逐字不变。

## 标签管理 `/tags`

面向**所有登录用户**的记账标签管理页（[`src/views/TagView.vue`](src/views/TagView.vue) + [`src/stores/tags.ts`](src/stores/tags.ts) + [`src/components/TagMultiSelect.vue`](src/components/TagMultiSelect.vue)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。标签与分类**逐条同构**：都是**账套内所有成员共用的词汇表**，也都是「记账时手工输入一个新名字即自动创建」，故维护能力同样不设门槛。页面**新建与修改统一走弹窗**（【新增】/【编辑】→ 表单 →【保存】落表），并支持停用/启用。

与分类的**唯一结构性差异是基数**：分类至多一个（它是交易头上的一列），标签可以有**任意多个**（落在 `hamster_transaction_tag` 子表里）。故本页比分类页多两处口径：

| 环节 | 行为 |
|---|---|
| 未选择账套 | 与分类页同：只显示「请先切换账套」的提示，**不渲染工具栏、表格与弹窗** |
| 跟随账套切换 | 与分类页同：`watch` 账套 `currentId` 重新拉取、未选择时清空；账套一变顺手关掉两个弹窗 |
| 新建（弹窗） | 字段**只有名称**（32 位以内）；每次打开都复位；**提交中禁止关闭** |
| 修改（弹窗） | **只可改名称**：所属账套一经创建即不可变更，弹窗内以**只读文本**呈现所属账套与创建时间 |
| 停用 / 启用 | 停用需二次确认（就地变为「确认停用 / 取消」），启用直接生效；按钮文案统一用「停用」，与后端软删除语义一致 |
| 显示已停用 | 勾选框驱动 `includeInactive`，勾选即重拉 |
| 表格 | 列：序号（页内行号）、标签名称、状态、创建时间、操作；空态 `colspan="5"`；**仅宽屏呈现** |
| 窄屏呈现（<1024px） | 表格隐藏，改为**卡片流**；空态与宽屏**逐字相同**（同一条件、同一文案表达式） |
| 提示位 | `error`（`ApiError.message`）与 `notice`（操作成功回执） |

与分类页的**三处刻意差异**（本页没有它们，不是漏了）：

- **没有「类型页签」**：标签不区分收入/支出/转账，同一份词汇表三类共用，没有可分的组。
- **没有「币种」**：标签与金额的计价单位无关，故本页比账户页少拉一次币种字典。
- **没有「用量」列**：哪笔交易挂了多少标签要跨表统计，而本页的职责是「维护词汇表」而不是「看统计」。真要知道某个标签下有哪些账，去「账目明细」页按它筛一次即可——那正是明细页筛选区提供标签多选的用途。

设计约定：

- **标签不区分收入 / 支出 / 转账**：与分类同一理由——标签是「这笔账的标注」，资金流向已由交易类型承载。
- **所属账套不可修改**：与分类同一理由；后端 `PUT` 的请求体同样只有 `name`。
- **一笔交易可挂任意多个标签、不设上限**：标签是多值标注，人为设一个数字只会让人在想多标的时候改不了账。
- **标签名在账套内不区分大小写唯一**，重名会被拒绝（409），与分类同一口径。
- **停用是软删除**：数据行保留、可随时重新启用；**已挂该标签的历史明细照常显示它的名称**，且手工输入这个名字时仍会归到它上面（不另建一个同名的，那样历史明细会裂成两份），明细页也仍可用它筛出那些账。
- **与账户页的最大差异（同分类页）：本页的「新增」不是唯一入口**：记账与改账时手工输入一个新标签名，后端会在当前账套内自动创建它。
- **不播种，空字典是正常起点**：与分类完全一致。
- **不做任何本地过滤**：标签没有可见性维度，账套内每个标签对每个成员都可见。
- **改名不影响既有明细**：关联行挂的是标签主键而不是名称字符串，改完之后历史明细直接显示新名字。
- **窄屏卡片流与宽屏表格是同一份数据的双呈现**：断点、`display` 切换、卡片底部保留完整操作区、卡片不呈现序号等口径与分类页**逐字相同**，理由见上一节。
- **窄屏菜单的「自动识别」是布局层的事，本页不参与**：同分类页。

## 收入 `/income`、支出 `/expense` 与 转账 `/transfer`

面向**所有登录用户**的三个记账入口（[`src/views/IncomeView.vue`](src/views/IncomeView.vue) / [`src/views/ExpenseView.vue`](src/views/ExpenseView.vue) / [`src/views/TransferView.vue`](src/views/TransferView.vue) + [`src/components/EntryRecordForm.vue`](src/components/EntryRecordForm.vue) + [`src/stores/transactions.ts`](src/stores/transactions.ts)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。三个页面各是一层壳（标题 + 说明 + 表单），**记账逻辑全在共用的 `EntryRecordForm` 里**，`mode` 决定记的是哪一种。

| 环节 | 行为 |
|---|---|
| 未选择账套 | 只显示「请先切换账套」的提示，**不渲染表单**——交易必然落在某个账套内 |
| 跟随账套切换 | `watch` 账套 store 的 `currentId`：重拉账户候选并**复位表单**，避免把账记到上一账套的账户上；未选择时清空账户 |
| 账户角色 | 收入页为「收入账户 + 来源账户」、支出页为「支出账户 + 目标账户」、转账页为「**转出账户 + 转入账户**」。文案全部取自 `MODE_META` 查找表，**转账页的两端都是必填的真实账户**——收入/支出的对手方可以留空或输入新名字，转账不行 |
| 表单栅格 | 字段按 `grid-template-columns: repeat(auto-fit, minmax(min(20rem, 100%), 1fr))` 排布：**单列宽度下限 20rem（320px）**，容器够宽时自动并成两列、不够宽时退回单列。下限不是随手取的——它要容下候选行里最宽的那一段「账户名 + 归属范围 + 七位数余额」（算法见设计约定）。`min(20rem, 100%)` 保证容器本身窄于 320px（如 320px 宽的窄屏机）时退回 `1fr` 而不是横向溢出 |
| 账户候选 | `accountsStore.list(false)`——**仅启用账户**（停用账户不应再记新账，其历史明细照常可在「账目明细」页查到，该页口径含停用账户，两者不同属刻意）。候选**先按所选币种过滤**（同一笔交易的两个账户必须同币种），**账户字段一律留空、不预填任何候选**（理由见设计约定）。**类型过滤按字段分别收敛**：主账户（转出账户）**恒只含钱账户**（资金/负债，`MONEY_ACCOUNT_TYPES`）；对手方候选**只在转账下**同样收敛，收入/支出的对手方照旧含往来账户（见设计约定）。转账的两个下拉都**不接受候选项之外的名字**（`:free-text="false"`），收支只有主账户如此 |
| 候选中的余额 | 每一候选行右侧显示该账户的**当前余额**，格式 `1,234.56 CNY`（千分位 + 固定两位小数 + 币种代码），与「归属范围」同格靠右、同色、`tabular-nums` 等宽对齐。余额是**附加信息**，一律中性呈现（负号表达符号），不参与类型主题色。它是派生值，记账后会变，故候选缓存在提交成功后作废（见下一行） |
| 候选行的三段内容 | **账户名 + 归属范围 + 余额**。归属范围（个人/公共）保留——它决定这笔钱记在谁账上；**归属人用户名不呈现**，因为单用户下每行都是同一个名字、零区分度，多用户下候选又已按可见性过滤过（他人个人账户根本不在候选里），那个名字与「这笔钱记到哪」无关；识别归属人的需求在账户管理页满足（那里照常显示）。一行要塞下三段而浮层宽度被输入框锁死，**弹性空间只由账户名承担**（另两段 `flex: none`），省下的横向空间全部还给账户名 |
| 候选缓存的生命周期 | **提交成功后清空**账户、分类与标签三份缓存（`accountsStore.clear()` / `categoriesStore.clear()` / `tagsStore.clear()`），**不在提交里重拉**；用户在本页接着记下一笔、表单内任意控件获得焦点时（`focusin` 委派）才补拉一次。币种缓存**不清**（全局字典，记账不会新建它，且它清空会让币种下拉当场空白）。**失败路径不清**：校验不通过或记账请求失败时缓存原样保留 |
| 币种 | 表单最上面的下拉，默认选中**系统默认币种**（无默认币种时取字典第一项，与「账户管理」新建账户表单同一口径）；**换币种会清空两个账户选择**——留着上一币种选好的账户，提交必然撞上后端的跨币种校验 |
| 分类（可选） | 币种与两个账户之后的搜索选择框，**可留空（即「未分类」）**，也可输入一个尚不存在的分类名——后端会在当前账套内自动创建它。候选取自 `categoriesStore.list(false)`（**仅启用分类**），输入即按关键词本地筛选；不在候选内且非空的名字会提示「提交后将自动创建」。**分类与币种无关，换币种不清空它**，也不区分收入/支出/转账 |
| 标签（可选，可多个） | 分类之后的 [`TagMultiSelect.vue`](src/components/TagMultiSelect.vue)：**可留空、可挂任意多个、不设上限**，每个已选标签是一枚可单独删除的 chip。候选取自 `tagsStore.list(false)`（仅启用标签），输入即按关键词本地筛选；输入一个候选里没有的名字后按【添加】或回车即成为 chip，**提交后由后端在当前账套内自动创建**（同分类）。**按【添加】或点选一个候选后，候选列表与「将自动创建」提示条一并收起、输入框同时失焦**（见设计约定；要接着加下一个标签，点回输入框即重新展开）。**标签与币种无关，换币种不清空它**，也不区分收入/支出/转账——三种记账类型的字段与占位完全一致（标签是「这笔账的标注」，与钱从哪到哪无关） |
| 金额 | `type="text"` + `inputmode="decimal"`，**刻意不用 `type="number"`**（见下）。`parseAmount` 用 `Number()` + `Number.isFinite` 而非 `parseFloat`，并要求 `> 0` |
| 发生时间 | `<input type="datetime-local">`，默认**此刻**（本地时区拼装）。提交前经 `toUtcIso` 折成 UTC 的 ISO 文本 |
| 提交 | 前端先校验币种 / 主账户 / 金额 / 时间 / 摘要 / 对手方 / 分类名长度 / 各标签名长度，不完整则**不发请求**；成功后**复位表单**并提示「已记录一笔收入/支出：摘要 账户名（对手方：X）」或「已记录一笔转账：摘要 转出 转出账户 → 转入 转入账户」，记了分类时末尾追加「 · 分类：分类名」、挂了标签时再追加「 · 标签：a、b」（顿号相连，**次序即提交次序**），可立即接着记下一笔。两段附加信息回显的都是**后端落定的结果**（手工输入的分类/标签名可能是刚被自动创建的），不是输入框里的文本——只有后端知道那个名字最终归到了哪一条记录上 |
| 重置 | 【重置】把币种回到默认币种、**账户清空**、金额与摘要/备注/分类清空、**已选标签全部清空**、时间回到此刻 |
| 提示位 | `error`（`ApiError.message`，恒为危险红）与 `notice`（记账成功回执 + 补拉失败时的说明，两者拼成同一条，**随记账类型着色**） |
| 类型主题色 | 页面标题、提交按钮与成功提示按记账类型着色：**收入绿 / 支出红 / 转账蓝**。其余控件（输入框、下拉、错误提示、说明块、【重置】按钮）一律不受影响 |

设计约定：

- **类型主题色只定义在 `base.css` 一处**：页面根元素标 `data-entry-mode="Income"｜"Expense"｜"Transfer"`，`base.css` 里三条 `[data-entry-mode]` 规则把该类型的三个令牌折成 `--entry-color` / `-soft` / `-strong`，标题、按钮、提示各自 `var(--entry-color, <兜底>)` 取用。于是**表单组件与三个 View 里都没有一处 `mode === 'Income' ? … : …` 的颜色分支**——颜色映射若散进组件，新增第四种记账类型时必然漏改某处。取用处的兜底值不能省：元素脱离带 `data-entry-mode` 的子树时退回品牌主色，与引入本层之前的表现一致。
- **转账蓝是独立的第四种语义色**：转账既不是收入也不是支出，而是账户之间的搬运，借用任一收支色都会把「搬运」读成「进出账」（账目明细页里一笔转账正是「支出 + 收入」两行的形状，类型标签是唯一的区分线索）。故 `--color-transfer` 与收支两色并列，而非复用主色。
- **hover 靠显式的 `-strong` 令牌，不用 `filter` / `color-mix`**：亮色下 hover 要更深、暗色下要更亮，方向相反，同一段 CSS 算不出两个结果，故 `--color-income-strong` / `--color-expense-strong` / `--color-transfer-strong` 在亮暗两套中各声明一次。
- **按钮文字色仍取 `--color-accent-contrast`**：亮色下为白、暗色下为深棕，在绿/红/蓝三个填充色下均已核对对比度。
- **三个入口各自独立组件，不共用同一个组件文件**：Vue 在任意两条路由指向**同一个组件**时会复用实例、切换不重新挂载，`/expense` 里填了一半的金额与摘要会残留到 `/income` 上。三个薄壳文件使切换必然重新挂载，共用的表单组件只承载逻辑不承载路由身份。
- **类型多了之后文案改成查找表**：`MODE_META` 按 `mode` 一次性给出按钮名、两个账户的字段名与摘要占位符。三元表达式在两种类型时还能读，涨到三种就会退化成「A ? x : B ? y : z」；查找表则是「哪种记账用哪套词」的平铺陈述，**新增类型时漏加一行会被 TypeScript 的 `Record` 当场拦下**。收入/支出两档的取值逐字未变。
- **转账的两个账户都必填、都不能按名新建**：转账的两个端点都是真实账户，没有「款项来自/去往账套之外」这一说，故留空无从落账；而按名新建出来的是往来账户，会绕开「只允许资金/负债账户」的限制。前端把对手方下拉切成 `:free-text="false"` 且不为空，后端另有四条专有校验兜底（见根 README 的端点契约）。
- **分类可留空，且输入新名字是特性不是漏洞**：留空即「未分类」，是后端接受的正常状态；输入一个候选里没有的名字，后端会在当前账套内**自动创建**它——记账人打出「宠物医院」时本就期待这个分类存在，弹一句「分类不存在」再让他去管理页建一遍是纯粹的往返。这与账户的 `:free-text="false"` 形成对照：**记到不存在的账户上没有意义，但记到一个新分类上完全有意义**。前端的长度预校验（32 位）只为少一次往返，真正的约束在后端。
- **分类候选取「仅启用」，但按名命中连停用分类也算**：候选列表用 `includeInactive: false`——停用分类不该再被推荐用于新记账。可用户若一字不差地打出某个**已停用**分类的名字，后端会命中那一条并挂上（而不是另建一个同名的启用分类，那会把停用行上的历史劈成两半）。故「候选里没有这个名字」并不等于「提交后一定会新建」，前端也不必为此拦一道。
- **分类与币种、账户都不联动**：分类没有币种、也没有账户范围，换币种不清空它，两个账户怎么选也不影响它。故它排在币种→账户那条联动链之外，是表单里**两个不参与联动的选择项之一**（另一个是标签）。
- **标签是多值的，且与分类的字段形态刻意不同**：分类至多一个（它在库里就是交易头上的一列），标签可以有任意多个（落在 `hamster_transaction_tag` 子表里），故不能复用 `CategorySearchSelect`——一个「选中即替换」的单选框表达不了「已选三枚、还想再加一枚」。`TagMultiSelect` 因此是一个**独立的兄弟组件**：已选项渲染成一排可单独删除的 chip，输入框永远空闲、随时可以再添一个。
- **一次提交里 `tagIds` 与 `tagNames` 是「并集」关系，与分类的「要么 id 要么名」不同**：分类只有一个名字，说了 id 就不必再说名。标签则可以**一部分从候选里点、一部分现场手打**，两段必须都生效，故后端把 `tagIds`（逐个查、查不到即 400 落在 `tagIds` 字段上）与 `tagNames`（命中即用、未命中即建）合并后再落库。前端因此不必把自己选的东西归类，而是**保持一个数组**：候选里点选的带真实 id、手打的是哨兵 id `NEW_TAG_ID = 0`，直到 `submit()` 那一刻才由 `splitTagRefs` 拆成两段。**刻意不给它们各留一个 ref、也不把已选中项做成「要么 id 要么名」的联合类型**——那样每删一枚 chip 都要先判断它属于哪一段，而用户心里「已选标签」就是一件事。
- **手打的名字若与候选重名，按候选的真实 id 走**（`commitDraft` 按名字回查候选项），于是后端不必再判一次重、也不会在账套内多出一个同名标签；**两个哨兵 chip 之间同样按名字去重**，大小写不敏感——与后端「账套内名称不区分大小写唯一」同一口径。
- **chip 一律从 `selected` 渲染，绝不到 `options` 里回查名字**：一笔账可能挂着**已停用**的标签，停用标签不在候选里（`includeInactive: false`），回查会让这枚 chip 显示成空白。
- **回车必须 `.prevent`**：标签输入框在 `<form>` 内，不拦的话回车会**提交整笔记账**，而此刻用户其实只想把刚打的名字变成一枚 chip——已输入的标签名会被静默丢掉。故 `@keydown.enter.prevent="commitDraft"`。同理，chip 的删除按钮是 `<button type="button">`，避免被当成提交按钮。
- **标签与分类、币种、账户都不联动**：标签没有币种、也没有账户范围，三种记账类型共用同一份词汇表，换币种不清空它。它是表单里第二个不参与联动的选择项。
- **标签框「选中即收起」——添加或点选后收起候选列表并让输入框失焦**：`collapseOptions()` 一处实现（置 `open = false` + 输入框 `blur()`），`choose()` 与 `commitDraft()` 两个调用点共用，**两件事都要做、缺一不可**：候选按钮是 `@mousedown.prevent`（按下不让输入框失焦，点击才落得到候选上），只关列表会留下「列表收起了、输入框却仍聚焦」的中间态，而本组件开列表的时机只有 `@focus` 一个（**没有** `@input` 开列表），用户接着敲字将看不到候选；反过来，点【添加】时输入框本就先失焦（`@blur` 已置假），但那之后 `commitDraft()` 才跑，故收起点仍须显式再置一次。这与 `AccountSearchSelect` / `CategorySearchSelect` 的 `choose()`（结尾 `open.value = false`、注释「并收起列表」）是**同一口径**——标签这份此前是三者里唯一的例外（`choose()` 与 `commitDraft()` 的结尾都是 `open.value = true`，点完候选列表仍挂着、遮住下方字段）。**取舍已知情**：回车提交草稿后输入框同样失焦，直接敲下一个标签名不会生效，需先点回输入框（点回即由 `@focus` 重新展开候选，故「收起」不会把选择框锁死）；**不要**改成「打字即重新展开」（给输入框加 `@input`）来回退这个口径。**改账弹窗（[`EntryEditDialog.vue`](src/components/EntryEditDialog.vue)）复用同一组件、一并生效**，不做按调用方的分叉。
- **金额输入必须是 `type="text"`**：`type="number"` 上的 `v-model` 会隐式转型（有效数字是 `number`、清空时是 `string`），一个 ref 里混着两种类型，`trim()` 之类的字符串操作会直接抛错。改用 `type="text"` + `inputmode="decimal"`：移动端照样弹数字键盘，而 `v-model` 恒为字符串。
- **`Number()` 而不是 `parseFloat`**：`parseFloat('12abc')` 会悄悄返回 `12`，把明显非法的输入当成合法金额提交。`Number()` 返回 `NaN`，配 `Number.isFinite` 一次拦下。
- **时间默认值与换算都必须走本地时间**：默认值用 `getFullYear` / `getMonth` / `getDate` / `getHours` / `getMinutes` 拼 `YYYY-MM-DDTHH:mm`，**不得**用 `toISOString().slice(0, 16)`（那是 UTC 时刻，东八区整体前移八小时）；提交时拆段后用 `new Date(y, m - 1, d, h, min)` 构造再由 `toISOString()` 折成 UTC，**不得**直接 `new Date('2026-09-23T10:00')`（按 UTC 解释该字符串，同样错位八小时）。
- **候选里的余额取自接口的派生字段，不在前端汇总**：用的是 `GET /api/accounts` 回传的 `balance`（该账户全部交易明细的有符号汇总，期初已计入其中），账户管理页用的是同一个字段。**不要用期初金额代替**，也不要在前端拿明细去算——有流水之后两者必然与后端脱节（同账户管理页的口径）。
- **账户字段的宽度下限由候选行的内容算出，不是随手取的数**：候选行要塞下「账户名 + 归属范围 + 余额」三段，其中只有账户名是弹性的（另两段 `flex: none`），故列宽下限必须按**最宽的一行**倒推——8 个汉字（13px × 8 = 104px）+ 归属范围「个人账户」（48px）+ 七位数余额「9,999,999.99 CNY」（等宽数字约 106px）+ 两道 0.75rem 间隙（24px）+ 候选行内边距（17.6px）+ 浮层内边距与边框（8.4px）≈ **308px**，取整到 320px（`20rem`）留 12px 余量。原来的下限 `12rem`（192px）下，候选行会把账户名截到只剩 4 个汉字左右。**用 `min(20rem, 100%)` 而不是直接写 `20rem`**：容器本身窄于 320px 时（320px 宽的手机内容区仅约 288px），固定下限会撑破容器造成整页横向滚动；`min()` 让下限随容器收敛，此时账户名以省略号截断——那是屏幕真的放不下，不是列宽没给够。该算式与结论在 `EntryRecordForm.vue` 的栅格注释里逐字同源。**上式是偏保守的上界估计**：实测 375px 窄屏下容器只剩 289px（375 − 滚动条 15 − 页面留白 32 − 表单内边距 38.8），8 个汉字 + 七位数余额的候选行仍无省略号，故 320px 的下限比必要值更宽裕，宁可宽一点也不要在真实的窄轨上截断。
- **余额是派生值，故「提交成功后作废候选缓存」是它的必然下一环**：这份缓存在进入页面与切换账套时各拉一次，此后不再更新；而一笔交易**必然**改变主账户与对手方的余额，对手方按名新建时还会多出一个本账套的往来账户。缓存留着，就是拿记账前的数去回答「这笔钱从哪出」，也会让下一笔再输入同一个新名字时仍被告知「不是已有账户」（提示与事实不符）。**分类与标签同理**——它们都可能刚被后端按名创建，留着旧字典会让下一笔再输入同一个新名字时仍不给候选。**币种不在此列**：它是全局字典，记账不会新建它。
- **「清空」与「补拉」分成两步，是刻意的**：清空是「不留旧值」的动作，取回则推迟到**下一次需要候选**的时候（用户在本页接着记下一笔、表单内控件获得焦点时，由 `<form>` 上的 `focusin` 委派触发）。之所以必须补拉，是因为主账户下拉 `:free-text="false"`——候选空着就选不出账户，用户会在本页无法接着记下一笔，而「记账后可立即接着记下一笔」正是本表单既有的口径。之所以不塞进提交里，是因为「这笔账记下了」与「候选数据几时取回来」是两件事，不该互相拖慢。
- **空窗期的占位文案不得说「没有」**：缓存被清空后候选为空，此刻既有的「当前币种下没有可用账户」/「暂无分类，可直接输入新分类名」/「暂无标签，可直接输入新标签名」都是**不实**的——账户、分类与标签并非不存在，只是尚未取回。故空窗内占位改说「正在加载账户…」/「正在加载分类…」/「正在加载标签…」（后两者的判据写在 `TagMultiSelect` 与分类选择框的 `placeholder` 计算里，与账户同源）。判据同权限分界：`Hidden` 是**权限**结论，不是「我不呈现它」；这里同理，空列表是**取数状态**，不是「没有」。
- **补拉清单收在一处（`loadMutableDictionaries`）**：账户、分类与标签三份缓存的取回只需一处 `Promise.all`，供「进页面 / 切账套」与「提交后补拉」两个时机共用。两处若各写一份清单，迟早漂移成「补拉了账户与分类、忘了标签」。
- **补拉失败不推翻成功提示**：账已经记下了，那是既成事实，不能用「记账失败」的口气去说它；但也不静默——候选里的余额与账户可能不是最新，用户有权知道。故失败说明进 `cacheNote`（「（账户、分类与标签列表刷新失败：…，候选可能不是最新）」）并与成功提示拼成同一条（`noticeText`），而不是复用 `errorMessage`；失败后「已清空」标记保持为真，下一次聚焦可以重试。
- **标签名长度预校验只为少一次往返**：前端的 32 位上限与后端 `TagEndpoints.NAME_MAX_LENGTH` 同值，真正的约束在后端（前端的长度判断与分类名走同一条校验链，错了不发请求）。
- **余额在浮层里不做语义着色**：它与「归属范围」同为中性 meta 信息，负余额靠 `-` 号表达即可。记账页的类型主题色（收/支/转账三色）只覆盖页面标题、提交按钮与成功提示条，**账户选择浮层不在其列**；引入红/绿只会让一个辅助信息抢走金额输入框的视线。同理，负债账户余额为负是正常财务状态，不加「欠款」文案与警示样式。
- **余额缺失时整段不渲染，而不是给占位标记**：这与「账目明细」页的加固口径（金额字段缺失不得静默降级，见 `AMOUNT_UNAVAILABLE`）看似相反，区别在于**「空白」在两处的语义不同**——那里三列的空白表示「这行没有收入」，是正常语义，字段缺失必须显式标记才不会被误读；这里余额是附加信息，整段不出现不会被读成「该账户余额为零」。但**绝不能渲染出 `NaN CNY`**，故仍以 `Number.isFinite` 拦一道。
- **停用账户不参与新记账**：候选只取启用账户。这是与「账目明细」页相反的取数口径（那里用 `includeInactive: true`），因为两者的目的不同——这里要的是「现在能把钱记到哪」，那里要的是「历史上钱动过哪」。
- **账本账户不需要前端过滤**：它是系统内部账户，后端从不返回它，故本页无需为此写过滤或禁用逻辑。
- **主账户候选恒只含钱账户，对手方候选只在转账下收敛**：主账户是「这笔钱记到哪个账户」，与「谁欠谁」无关——记到往来账户上的流水在「账目明细」页不呈现（那一页只呈现钱账户上的明细），记录当场就会变成查不到的一笔，故三种记账类型的主账户候选口径一致、一律只留资金/负债。**对手方是刻意相反的**：收入/支出下「支出 现金 → 老王」正是记到往来账户上的写法，把往来账户挡在这里等于砍掉这个用法；只有转账的两端都必须是钱（钱在两处「钱」之间挪动），后端也会 400。故一个表单里的两个账户字段**候选集合不同**（`primaryAccountOptions` / `counterpartyOptions`），不是同一个 `accountOptions` 改个过滤条件。
- **类型清单只有一处**：`MONEY_ACCOUNT_TYPES`（资金/负债）同时供**转账两端、记账页主账户、账目明细的账户筛选项**三处使用，是后端 `AccountTypeExtensions.IsMoneyAccount` 的前端镜像（`IsTransferAccount` 只是它在转账语境下的名字，两者恒等）。分写成三份清单，将来新增账户类型时必然有一处被漏改。
- **账户一律不预填，币种仍然预填**：账户（收入/支出/转出账户）在初始打开、提交成功后、点【重置】三处**都留空**，每次都须显式选择。账户是「这笔钱记到哪」的决定性信息，预填第一个候选等于把一个默认值伪装成已经做过的决定——不察的人会把账记到并非本意的账户上，且这类错误在明细里与正常记账无从区分；而留空的代价（多一次点选）远小于记错账户的代价。**币种则在三处都回到系统默认币种**，两者口径不同属刻意：币种只是账户候选的筛选前提（候选先按币种过滤），它本身不决定钱记到哪，预填它只省事不误导。清空并未削弱可操作性：`AccountSearchSelect` 在关键词为空时列出**全部**候选，聚焦即见；空账户由 `submit()` 的「请选择{主账户}」在校验链前端拦下（不发请求），字段名还随记账类型变（收入账户 / 支出账户 / 转出账户）。
- **记账后清空而非保留**：金额与摘要是逐笔的，沿用上一笔只会导致误提交；发生时间则复位为此刻（补记往日是少数情形，保留旧值更容易出错）；账户同属逐笔的选择，同样复位为空。**清掉的是两个层次的东西**：字段（选中项，由 `resetFields` 复位）与**候选数据本身**（由 `clearOptionCaches` 作废后按需补拉）——前者是「这一笔填了什么」，后者是「有哪些可选、各自的余额是多少」。
- **错误文案由 `ApiError.message` 给出**，与其余页面一致。

## 账目明细 `/entries`

面向**所有登录用户**的账目明细查询页（[`src/views/EntryQueryView.vue`](src/views/EntryQueryView.vue) + [`src/stores/entries.ts`](src/stores/entries.ts) + [`src/stores/accountSetPreferences.ts`](src/stores/accountSetPreferences.ts)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。在当前账套内按**时间区间**、**账户（可多选）**与**标签（可多选）**筛选交易明细，按业务发生时间正序分页呈现，并可对可编辑的行**就地修改**（改的是**整笔交易**，见下表「改账」行）。**账户与标签的勾选会按「你 + 当前账套」保存到个人账套配置里**（`hamster_account_set_preference`），下次进入本页自动恢复并按它查询；日期区间不在其中（见下表「筛选条件的保存与恢复」行）。

| 环节 | 行为 |
|---|---|
| 未选择账套 | 只显示「请先切换账套」的提示，**不渲染筛选区与表格**——明细一律挂在账套下，展示一个不属于任何账套的空列表只会误导 |
| 跟随账套切换 | `watch` 账套 store 的 `currentId`：清空结果 → 重拉账户与标签两份筛选候选 → 恢复**该账套里保存的**筛选条件并立即查一次；未选择时同时清空账户、标签与明细。**仅靠 `onMounted` 会残留上一账套的明细**；个人配置同样按账套隔离，恢复的是「这个账套里的那一份」，不是上一个账套的 |
| 时间区间 | 两个 `<input type="date">`，默认**本月 1 日 ~ 今天**（本地时区）。两端均为**闭区间**：起始取当日 `00:00:00.000`、结束取当日 `23:59:59.999`，再折成 UTC |
| 账户多选 | 复选框列表，数据源为 `accountsStore.list(true)`——**含已停用账户**，并给它们打「已停用」标签。候选**只含钱账户**（资金/负债）：账本账户由后端排除，**往来账户由本页排除**（明细行本就不含它们，候选留着只会造成「勾了也查不到」的空档）。默认**全选**，提供【全选】/【全不选】与「已选 X / Y」计数；账户多时**只在该区域内滚动**，不把页面撑长 |
| 标签多选 | 与账户栏**同构但并列的第二块面板**：复选框列表，数据源为 `tagsStore.list(true)`——**含已停用标签**（停用是「不再供新记账选择」而不是「历史上从未用过」，而本页查的正是历史）并给它们打「已停用」标签。标签**不校验「至少选一个」**：空即「不限标签」，这与账户的必选刻意不同——没挂标签的账占多数，把它当漏填的条件会让默认视图查不出东西来。也**没有【全选】**（账户那份才有）：标签的「全选」与「不限」只差「含不含没挂标签的账」，给一个【全选】反而会让人以为「这就是全部」 |
| 查询 | 条件是**草稿**，改动输入不立刻发请求（避免边打字边查询），点【查询】才落成已应用条件并从第 1 页取数；【重置】回到「本月 + 全选账户 + 不限标签」并立即查询。**这两个用户动作都会把条件保存到个人账套配置**（进入页面时那次自动查询不保存） |
| 筛选条件的保存与恢复 | 进入页面（含切换账套）时读一次个人配置，把它**与当前候选求交**后落到草稿上：账户主键不在候选里的丢弃、一个都不剩则回落到全选（「至少选一个账户」是硬校验，恢复出空集会让页面一进来就查不出东西）；标签主键同理求交，求交为空正好落回它本来的默认值「不限标签」。恢复所得与默认视图（全选 + 不限）不同时才在提示位补一句「已恢复上次保存的筛选条件」。**写库只发生在【查询】与【重置】上**：进入页面那次查询是「读出来再查」，把同一份数据原样写回去只是白跑一次往返 |
| 页面级说明 | 两块面板**之外**有一行 `.save-note`，写明「按『你 + 当前账套』保存、下次自动恢复」与「日期区间不保存」——它管的是账户与标签两处的勾选，塞进任何一块面板都会让人以为只管那一块。故用独立类名（与面板内的 `.picker-hint` 共用同一套排版，字号与透明度一致） |
| 前端校验 | 三处均在发请求前拦下：日期空 → 「请选择完整的时间区间」；起始晚于结束 → 「结束日期不能早于起始日期」；一个账户都没选 → 「请至少选择一个账户」。**标签不在此列**（见上） |
| 明细行 | 只呈现**钱账户**（资金/负债）上的明细：账本账户是系统内部账户，往来账户记的是「谁欠谁」而非「钱放在哪」（它上面的账是另一本账），两者都不作为明细行出现。被排除的行**只是不呈现**，库内数据一行未动——那笔交易照旧配平、账户余额照旧计入。往来账户照常在**对手方列**显示名字（「支出 现金 → 老王」被排除的是「往来账户作为记账主体」，不是「往来账户这个信息」） |
| 表格 | **仅宽屏呈现**。列：序号（页内行号 `index + 1`）、发生时间、账户、**收入**、**支出**、**净额**（三列均右对齐 + `tabular-nums`；**收入/支出两列一律显示为正数、不带 `+`/`-`**，靠列头与语义色区分方向——收入列恒绿、支出列恒红；**只有净额列带符号**，按正负着色）、对手方、摘要（附弱化的交易类型）、**分类**、**标签**、备注、**操作**；空态 `colspan="12"` 且**带上本次查询的条件概要** |
| 本页小计 | **仅宽屏呈现**。`<tfoot>` 一行：`colspan="3"` 的「本页小计」+ 收入合计 + 支出合计 + 净额合计 + `colspan="6"` 留白。只统计**当页**（跨页合计会让标题名不副实），空页时不渲染。**收入/支出两项与明细行同列同口径**（去符号显示正数），净额合计仍带符号。窄屏下同一组数字改由卡片流末尾的汇总条呈现，取值同为 `pageTotals` |
| 改账 | 操作列给可编辑的行一个【修改】按钮（`isEntryEditable`，见下），点开 [`EntryEditDialog.vue`](src/components/EntryEditDialog.vue)：**改的是整笔交易**（借贷两条明细一并改写、方向不变，类型与币种只读呈现），**标签也在可改之列**。保存成功后关闭弹窗、重新查询明细、账户与标签候选（余额是派生值，改完重新取即新值；标签可能刚在弹窗里手打新建，候选需一并刷新），提示条改写为「已修改一笔转账：… 转出 X → 转入 Y · 分类：… · 标签：a、b」。弹窗**加宽到 44rem**（全站 8 个字段里最多的一个，见设计约定）且字段区为**两列自适应栅格**；分类候选**只含启用分类**（本笔当前那一枚也不例外，输入框照旧回填、后端按名归到原分类上，字段下方有一句如实说明）。**不可编辑的行不出按钮**，也不出禁用态按钮 |
| 窄屏呈现（<1024px） | 表格与 `<tfoot>` 隐藏，改为**卡片流**（`ul.cards`，一条明细一张卡）+ 末尾**汇总条**（`.totals`）：卡片头部左侧是收支标签 + 交易类型、右侧是金额（即为该行**净额**，带 `+`/`-`，按正负着色），其下依次是「账户 → 对手方」「摘要」「时间 · 分类 · 标签 · 备注」，末尾是卡片自己的【修改】按钮（`.card-actions`，条件与宽屏同一份 `isEntryEditable`）——表格在窄屏是整块隐藏的，这个按钮就是手机上唯一的管理入口，故它**只在该断点内**放大到 `min-height: 2.25rem` + `13px`（宽屏下的按钮尺寸对触屏偏小，而宽屏尺寸逐字不变）；汇总条的收入/支出无符号、净额带符号，与宽屏 `<tfoot>` **逐字同值**；空态与宽屏**逐字相同**（同一份 `emptyText`），空页时汇总条不渲染 |

设计约定：

- **一行是一条明细，不是一笔交易**：一笔交易由借贷两条明细构成，当两侧都落在所选账户上时就会呈现**两行**。把同笔交易合并成一行需要引入「净额」概念，而那与「查明细」的目的相反。**一笔转账正是这种「两侧都可见」的典型**：它落成「转出（支出列）+ 转入（收入列）」两行，形状与一笔支出加一笔收入无异，**摘要旁的「转账」类型标签是唯一的区分线索**，故该标签不能省。
- **金额按收入/支出分列，带符号金额由后端派生**：后端在明细 DTO 上回传 `signedAmount`（`amount` 按 `direction` 取符号：借方为正、贷方为负），前端只做格式化与分列——**不自行折算符号**。换算的定义在后端的 `EntryDirectionExtensions.SignedAmount`，与账户余额汇总 `SumSignedAmountsAsync` 共用同一处；在列表里再算一次就是第二个语义源。
- **符号只留给净额列：收入/支出两列显示为正数**：列头已经写明「这一列是收入 / 支出」，同一行又只有一列有值，再补一个 `+` / `-` 是把方向说第三遍；故 `incomeText` / `expenseText` 走 `formatUnsigned`（取绝对值），方向由**列头 + 语义色**表达。净额列**必须**继续用 `formatSigned`：它是唯一「一格容纳正负两种结果」的位置，符号就是它的方向通道。**「本页小计」的收入/支出两项与明细行同口径**——同一列上下若出现「明细 `100.00`、合计 `+1234.56`」两种写法，等于同列两套规则。这只是**呈现约定**：去符号发生在「已判定属于哪一列」之后的格式化环节，分列判据仍是 `signedAmount` 的正负。异常路径同样不动——非有限数在 `Math.abs()` 之前就被拦下并显示「金额异常」，绝不能渲染出 `NaN`。
- **「借/贷」不呈现给用户**：复式记账是数据的组织方式，不是普通人读账的方式。`direction` 仍由接口如实回传（账本的底层事实），但页面上没有方向列，增减由收入/支出两列与净额列的正负号表达。
- **收入绿 / 支出红是语义色，不来自品牌色板**：`--color-income` 表达的是「金额正号」、`--color-expense` 表达「金额负号」，均与主题色无关。在明细页，这两色同时承担「这行是收入还是支出」的区分职责（收入/支出两列的金额不带符号，颜色是除列头之外的唯一通道）；支出红直接复用 `--color-danger`，全站因此仍只有一个红。两者均在 `base.css` 亮/暗两套中齐备（暗色下绿色提亮以保证对比度）。三者连同 `--color-transfer` 一起也充当记账页的类型主题色，详见「收入 / 支出 / 转账」小节。
- **不做任何可见性过滤，但做类型呈现分组**：后端只返回「挂在我可见账户上」的明细，账户多选的候选也由后端按可见性过滤（他人在个人账户根本不在列表里）。本页**不写第二份可见性判断**——前端的可见性只是体验层，篡改本地状态只会拿到一批 400 / 403。与之并列的是另一件事：本页把候选按下拉用途**按类型分组**（只留钱账户），那是**呈现分组**，不是权限——后端接口不按类型过滤（账户管理页的页签与记账页的对手方候选都需要往来账户），故只能由消费方各自收敛。
- **账本账户不出现在账户多选里**：它是系统内部账户（每账套恰一个，由系统在首次需要对手方时自动创建），后端从不返回它，故本页无需为此写过滤或禁用逻辑。它在明细里作为**期初余额、收入、支出共同的对手方**出现，显示为「账本」；**转账不写账本账户**（它的对手方是另一个真实账户），故一笔转账的两行对手方都是 `Account` 档。
- **往来账户不作明细行，但照常出现在对手方列**：本页回答的是「钱动在哪个账户」，而往来账户记的是「谁欠谁」而不是「钱放在哪」——它的余额与来往由**账户管理页**承担。故后端把明细行收在钱账户上（`AccountTypeExtensions.IsMoneyAccount`，与转账两端的限制是同一个集合，故只定义一处），本页的候选项也随之只留钱账户。两侧分界必须一起看：往来账户**作为记账主体**被排除，**作为对手方**照旧显示名称（「支出 现金 → 老王」的那行账户是现金、对手方是老王），故后端的行过滤只收窄**行集合**、不动**账户名来源**——名称来源若一并收窄，对手方会退化成 `Hidden` 档渲染成「—」，等于把用户自己的往来账户伪装成不可见账户。
- **候选的排除必须在后端、候选的过滤可以在前端**：明细行的排除只能在后端做——前端过滤会让 `total` 与实际渲染的行数对不上（「共 12 条却只显示 8 行」）；而候选项的排除在前端做，因为账户接口不能按类型过滤（账户管理页需要完整列表）。**同一件规则的两半落在不同层，判据是「哪一层能让数字自洽」**，不是随意分工。
- **既有数据里两条明细都落在往来账户上的交易不再出现**：例如主账户选了往来账户、对手方又按名新建了另一个往来账户。这不做迁移、不做豁免——豁免会让规则多出「除…之外」的第二档，且要为历史数据维持一条永不使用的代码路径。记账页的主账户候选排除往来账户，正是让这种形状**不再产生**。
- **对手方分档呈现，前端不给「回退到 Id」的分支**：`Account` 档直接用 `counterpartyName`；`Ledger` 显示「账本」；`Hidden` 与 `None` 显示「—」。后端对不可见对手方**连主键都不回传**，故前端也不存在任何「拿到 Id 再想办法」的路径。`Ledger` 的标签曾是「期初」，收入/支出落地后改成了「账本」——同一个账户现在也是每一笔收支的对手方，再叫「期初」会把一笔支出标成期初。
- **分类是独立一列，不并入摘要**：分类是可按之聚合的维度（「这个月餐饮花了多少」），塞进摘要文本里就再也筛不出来；摘要旁的交易类型标签是**背景信息**，那是它弱化呈现的理由，分类不是。它与备注同属「每行都要读得到、又都不抢金额视线」的信息，故列在摘要与备注之间。
- **未分类显示「—」而不是空白**：`categoryText` 返回 `categoryName ?? '—'`，与对手方的兜底同一处理。留空会被读成「渲染漏了」，而「未分类」本身是有意义的信息——记账时分类本就是可选的。
- **分类名由后端给出，前端不拿字典反查**：明细里显示的是后端回传的 `categoryName`。**不要**用前端 `categories` store 按 `categoryId` 反查——那个列表只装当前**启用**分类，且未必已加载，一旦查不到就会把一笔有分类的账渲染成「未分类」。后端回传的名称已天然处理了两件事：分类改名后历史明细显示新名字，以及已停用分类的名称照常显示（那些账确实发生过）。**标签同理**（见下一条）。
- **标签名同样由后端随明细下发，不用标签字典反查**：`Entry.tags` 是后端给的 `{ id, name }` 数组，理由与分类逐字一致——标签候选只装当前启用标签，且一笔账可能挂着**已停用**的标签，反查会让它显示成空白。**「一笔交易的两条明细显示同一组标签」不是重复**：标签挂在整笔交易上（`hamster_transaction_tag` 的外键是交易主键而非明细主键），两条明细本就该看到同一份。
- **标签是多值的，与分类分列且列宽可折行**：分类至多一个（单值、单行读得完），标签可以有任意多个且不设上限，一整行标签撑宽单元格会把金额几列挤出视野。故标签列**允许折行**（不加 `white-space: nowrap`）并用 `overflow-wrap: anywhere` 兜底超长标签名（上限 32 位）——折行只让该单元格变高，其余列不受影响。呈现为**顿号连接的一行纯文本**（`tagText`，无标签时显示 `—`），**不做成一排徽标**：同一行里分类是文字、标签是徽标会让人以为两者不是同一类东西，而标签数量既然不设上限，徽标排一行也未必放得下。
- **标签筛选是「任一命中」而不是「全都要有」，且与账户维度是「且」的关系**：勾了三个标签想问的是「这三类我都想看看」，故后端用 `EXISTS` 子查询而不是 `JOIN`（`JOIN` 会让一笔挂三枚标签的交易在结果里出现三次、把 `total` 撑大，而 `EXISTS` 保证 `total` 与真正渲染的行数恒等）。两个筛选维度各自独立收窄：都要同时满足。**顺序与次序不参与**：标签是集合，用户勾选的先后不该改变结果。
- **日期默认值必须用本地时间拼装**：`getFullYear` / `getMonth` / `getDate` 拼 `YYYY-MM-DD`，**不得**用 `toISOString().slice(0, 10)`（那是 UTC 日期，东八区在本地 08:00 之前会整体前移一天）；日期 → UTC 也**不得**直接 `new Date('2026-09-01')`（按 UTC 解释，区间整体错位），必须拆三段用 `new Date(y, m - 1, d, ...)` 构造。
- **筛选候选含已停用账户**：账户是软删除，停用账户上仍有历史明细（后端也按 `includeInactive: true` 取可见账户集）。若候选漏掉它们，那些明细将永远无法被筛出来，而数据其实还在库里。
- **交易类型弱化呈现、不占一列**：它是明细的背景信息，与摘要同格呈现；取值经 `transactionTypeLabel` 兜底——后端新增类型而前端尚未同步时显示原字符串，而不是渲染成空白。
- **`CounterpartyKind` 类型含 `None`**：后端枚举有四个取值，虽然当前数据模型下 `None` 不应出现（每笔交易恒有借贷两条），类型与标签表仍为它留位——漏掉它会让标签表在运行时落空（返回 `undefined` 渲染成空白），比多写一行更糟。
- **未选账套时的 400 是预期行为**：后端对不带 `X-Account-Set-Id` 的请求返回 400「请先选择账套」，这正是页面在无账套时不发请求的原因。
- **筛选条件存在后端、不存 `localStorage`**：「我习惯怎么看账」是账号级偏好，换台机器、换个浏览器应当跟着人走；而 `localStorage` 只在那台机器的那个浏览器里有效，还会跟着「换个人登录」继续生效。落点是 `hamster_account_set_preference` 表，按**「账套 + 用户」唯一**（同一账套内不同成员各存各的，切换账套时读到的是该账套里的那一份）。
- **只记账户与标签，日期区间刻意不记**：日期是「我**这次**想看哪一段」——补查一笔上月旧账之后，下一次进来若还停在那个区间，用户会以为本月没有流水。故每次进入都回到默认的「本月 1 日 ~ 今天」，而账户与标签是「我**平时**怎么看账」。这条取舍写在页面级说明里（`.save-note` 末句），不让它成为一条只活在文档里的约定。
- **进入页面不写库，只有【查询】与【重置】写库**：进入页面时那次查询是「把刚读出来的条件再查一遍」，把同一份数据原样写回去只是白跑一次往返；而【查询】与【重置】都是用户明确表达「我以后也这么看」的动作（【重置】的落库尤其不能省——否则下次进入又恢复成重置前的条件，按钮看起来像没生效）。`search({ persist })` 用参数区分这两类调用，而不是在调用点上各写一套。
- **恢复时与当前候选求交，账户求交为空则回落到全选**：保存下来的那一份是「当时可见的钱账户」，而账户可能已被停用（仍留在候选里）或已不可见（不在候选里）。账户**必须**回落——「至少选一个账户」是本页的硬校验，恢复出一个空集会让页面一进来就查不出东西，而用户并未做错任何事；标签求交为空就是空，正好落回它本来的默认值「不限标签」（标签本就不校验「至少选一个」）。故「打开页面看到的是什么」与「库里存的是什么」可能不同：库里那一份始终是保存当时的如实记录。
- **读配置失败不阻断页面**：回落成「本月 + 全选 + 不限标签」照常查一次，并在提示位说明（`…（本次按默认条件查询）`），用户手上仍是一个能用的页面。这与「补拉候选失败」的处置同一口径。
- **「已恢复上次保存的筛选条件」只在与默认视图不同时才说**：判据取「账户数是否等于候选总数、标签是否为空」（`isDefaultSelection`），而不是「是否曾走过恢复分支」——恢复到一份与默认等价的配置本来就不含新信息，这句话纯属噪音。用户自己点【查询】后它立即清掉（上一条恢复说明当场过期）。
- **保存失败只补一句说明，不推翻刚查出来的结果**：账目已经查出来了，那是既成事实；提示的语气也须与「查询失败」区分开——用户下次进来看到的是旧条件，不是「账查不出来」。
- **配置 store 不缓存读到的值、也没有 `loading`**：它装的是一个**状态的来源**，而消费方（本页）自己就持有那份草稿。在 store 里再存一份会多出一个真值源，账套切换后忘了刷新它，就会把上一账套的筛选条件恢复到这一账套上——这正是本功能最容易出的错。一次性读、一次性写，页面拿到什么就是什么。
- **改账弹窗加宽到 44rem 并把字段改成两列栅格**：它要装 8 个字段，26rem 的窄列（账套选择弹窗的尺寸）下只能竖排、字段区必然滚几屏。44rem = 704px 是 `.fields` 放下**两列 20rem**所需的最小宽度（2 × 320px + 0.7rem 列间距 ≈ 651px，加两侧 1.35rem 内边距 ≈ 694px，留 10px 余量）；再宽也不会多出第三列（三列需要 971px，超过多数笔记本的可视区），故到此为止。**全站弹窗不再只有一种尺寸**：宽度跟着内容走，而不是反过来让 8 个字段挤进 26rem 里去。栅格用 `repeat(auto-fit, minmax(min(20rem, 100%), 1fr))`——窄屏自动并为一列、无需媒体查询（与记账表单同一做法），并用 `align-content: start` 避免字段区在字段少时被拉高摊开。
- **改账弹窗的分类候选只含启用分类，本笔当前那一枚也不例外**：停用即软删除，语义是「不再供新记账选择」，而改账同属「重新选一次分类」（与记账表单、账户候选同一口径）。**但「候选里没有」不等于「这一笔不能保持原样」**：本笔当前分类可能正是已停用的，此时输入框仍回填它原本的名称（那个名字取自交易自己的数据而非候选表），保存时后端按名匹配**含已停用分类**、会归到原来那一行上、**不会**新建一个同名的。候选与输入框因此可能对不上，选择框还会按自己的逻辑提示「不是已有分类，提交后将自动创建」——那句话在这种情形下是不准确的，故由字段下方的 `field-hint` 如实说明（与「对手方是系统账本账户」那句同一做法）。**不改选择框那句文案**：它同时服务记账表单，为一个只在本弹窗成立的例外去改公共组件，会让另外两处调用点也读到一句与它们无关的说明。**取数仍取全量**（`list(true)`）——判「本笔那一枚是不是已停用的」必须有全量在手，把取数一并收窄成 `list(false)` 就判不出来了；「取全量」与「候选列什么」是两件事。
- **窄屏卡片流与宽屏表格是同一份数据的双呈现，用 `display` 切换**：两份 DOM 始终并存，由本站**唯一**的 1023px 断点（定义在 [`src/App.vue`](src/App.vue)）决定谁可见。页面级适配**不得自建断点或改用 JS `matchMedia`**——两个断点一旦错开，就会出现「表格与卡片同时可见 / 同时不可见」的窗口。这里的 `display: none` 与「隐藏同一份内容里的冗余字段」不是一回事：那类隐藏（如账户管理页不呈现类型列）删掉也不影响信息完整性，属死代码；这里是**某一时刻整份呈现都不适用**，隐藏是它的定义。前提是「任一时刻恰有一份进入无障碍树」，故两份呈现不能同时可见。
- **卡片只给一个金额，不摆收入/支出/净额三列**：卡片是**单行**视角，而单行上净额恒等于收入或支出中非零的那一个（三列只在合计处才分岔，见「本页小计」）。三列摆在卡片里必有两列是空白，反而不如一个带符号的金额加一个收支标签读得快。**序号同理不呈现**：它只是表格里「第几行」的计数，卡片本身已是独立一块，序号既不便于回指、也占掉金额的位置。
- **卡片的收支标签由金额符号派生，不看 `direction`**：`sideText` 与宽屏两列同源——`signedAmount > 0` 显示「收入」、`< 0` 显示「支出」、`=== 0` 与金额缺失时**留空**（零值行在宽屏下同样是两列皆空，卡片不得把它说成收入）。定义收支的是符号本身，`direction` 只在后端派生符号时用一次。
- **窄屏菜单的「自动识别」是布局层的事，本页不参与**：侧栏收成抽屉、按 `router-link-active` 高亮当前页、路由跳转后自动收起，均由 [`src/App.vue`](src/App.vue) 的 1023px 断点与 `watch(route.fullPath)` 统一提供，新增页面**天然获得**，不需要（也不应该）在页面里写任何菜单相关逻辑。
- **改账改的是整笔交易，不是被点的那一行**：一笔交易由借贷两条明细构成，只改其中一条会让复式记账当场失效（借不等于贷）。故弹窗提交的是**整笔**（`PUT /api/transactions/{transactionId}`），后端在同一个事务里改写两条明细（金额同步、方向不变）与交易头（发生时间、摘要、备注、分类），**标签关联行也一并替换**。**提交的是交易主键，不是明细主键**——明细主键只用于查询侧的稳定排序。
- **改账时标签是「整组替换」而不是「增量挂载」**：弹窗一开就把该笔现有的标签全部铺进选择框（`[...entry.tags]`），提交的是**这个时刻的完整一组**——去掉了哪一枚就是要去掉它。故后端收到的是「这一笔现在挂这几个」，与「只增不减」的增量语义不同；不带该字段与带空数组也不是一回事（空数组即「一个标签都不挂」，是合法的显式意图）。
- **「重新计算相关账户余额」在这里表现为「改完重新查询」**：余额是明细的派生值（后端 `SumSignedAmountsAsync`），库内没有余额列，故改账**不需要、也不存在**一次额外的重算调用。弹窗保存成功后本页重新拉一次明细、账户与**标签候选**，余额自然呈现为新值——界面上的余额从来都是查出来的。标签候选一并刷新是因为弹窗里可以手打一个新标签名（后端当场在当前账套内建出它来，与记账同一口径），留着旧词汇表会让筛选区里少一个刚被用过的标签。
- **点哪一行都能改，两个端点由 `isPrimary` 还原**：`isPrimary` 标出主账户那条明细（按类型的方向定出：收入记借方、支出与转账记贷方那条），故点转账的**任一行**都能把弹窗的两个账户端回填正确——点的若是对手那条，主账户就是它这行的对手方。**不做**「点了哪一行就当主账户」之类的就近猜测：那会让同一笔转账在两次点击下产生两种结果。
- **不可编辑的行不出按钮，而不是出禁用态按钮**：`isEntryEditable`（[`src/stores/entries.ts`](src/stores/entries.ts)）的两个判据与后端准入同源——① 类型可记账（期初余额由系统生成，改它会让「金额恒等于账户期初余额」「每账户至多一条」两条不变量同时失效，后端 400）；② 对手方档位为 `Account` 或 `Ledger`（`Hidden` 表示那笔账的另一半在别人名下，改它等于替别人改账，后端 404）。禁用控件占位会让用户去猜「为什么不能点」，而这两个原因都不是用户在当前页面能解决的。
- **前后端各拦一次，拦的是不同的事**：前端拦的是**体验**（空摘要、零金额、转账没选转入账户、两端同账户、标签名超过 32 位——都在发请求前就地报错、不发请求），后端拦的是**准入**（交易归属哪个账套、两个端点是否都在操作者这一侧、币种是否一致、账户是否可见、标签是否属于本账套）。两处各写一遍是必要的：前端少一次往返，后端不能被绕过；**前端拦下的项不代表后端可以不判**。
- **角色的叫法只有一份**：弹窗的「转出账户 / 转入账户」等字段名与记账表单共用 store 里的 `TRANSACTION_MODE_META`（经 `transactionModeMeta(type)` 取用）——同一对端点若各写一份文案，用户会在两个页面读到两种叫法。期初余额没有「主账户 / 对手方」这两个角色，故该函数对它返回 `null`。
- **候选按币种收敛，但币种取不到时不过滤**：改账不带币种字段（币种随主账户走），弹窗的候选因此按主账户的币种过滤；币种无从得知时（账户列表尚未加载）**退回不按币种过滤**——用一个空币种去筛会把候选清空，连「原样保存」都做不到。
- **弹窗先把焦点交到面板，再去拉分类候选**：Esc 关闭挂在**面板**的 `keydown` 上，焦点不在面板里键盘就整段失效（取消按钮仍可用，故这种失效更难被发现）。把它挂在一次网络请求之后，等于让「能不能按 Esc」取决于那次请求的快慢与成败；分类候选晚一步到位不影响先读到内容。
- **保存成功后提示条要写在重新查询之后**：`load()` 会把 `notice` 改写成「共 N 条明细」，故 `onEdited` 里的赋值必须排在 `await load()` 之后——顺序颠倒的话，用户看到的是条数，而不是「已修改一笔转账」。

## 用户设置 `/settings`

面向**所有登录用户**的个性化页（[`src/views/SettingsView.vue`](src/views/SettingsView.vue)），路由只标 `requiresAuth`——**不带** `requiresAdmin`，菜单项同样不设 `adminOnly`。页内含两个区块：

| 区块 | 内容 |
|---|---|
| 修改密码 | 原密码 + 新密码 + 确认新密码，提交 `POST /api/auth/change-password` |
| 关于 | 产品名、版本号、一句话简介、技术栈、开源许可（MIT）与版权 |

设计约定：

- **改密必须提供原密码**：仅有令牌不足以改密（否则令牌泄露即可直接夺号），后端校验原密码失败时统一返回 400「原密码不正确」。
- **改密成功后前端主动登出**：成功提示下方提供「前往登录」链接，用户须用新密码重新登录。见下方「已知边界」——这是体验层的收口，不是服务端的强制失效。
- **改密失败不触发全局登录失效处理**：请求层传 `handleUnauthorized: false`，400 是业务校验失败，不应被误判为登录态过期。
- **关于信息集中在 [`src/config/appInfo.ts`](src/config/appInfo.ts)**，页面只做渲染。
- **版本号以 `package.json` 为单一数据源**：`vite.config.ts` 读取后在构建时经 `define` 注入全局常量 `__APP_VERSION__`（类型声明见 [`env.d.ts`](env.d.ts)），页面与 `appInfo.ts` 均不硬编码版本号。当前版本 `0.1.0`。

> **已知边界**：JWT 不携带密码版本，**改密（乃至被管理员停用）都不会使已签发的旧令牌立即失效**，旧令牌在其 1 天有效期内仍可访问非管理接口。前端改密后主动登出只是让本人这台浏览器不再沿用旧令牌；若需要「改密即踢下线」，需在服务端的令牌校验环节回查用户状态（本项目当前未实现）。

## 密码重置 `/reset-password`

管理员生成的重置链接落地页（[`src/views/ResetPasswordView.vue`](src/views/ResetPasswordView.vue)），**免登录**（路由 `meta: { layout: 'blank' }`，不带 `requiresAuth`）——被重置的用户多半处于未登录态，要求登录会让链接形同虚设。

- 链接形如 `/reset-password?username=xxx&token=yyy`，用户名由查询参数**预填但可修改**：预填只是省事，真正的「用户名 + 令牌」双因子匹配由后端完成，篡改它只会得到统一的失败提示。
- 缺少 `token` 参数时给出「重置链接不完整」的明确提示，并禁用提交按钮，而不是让用户对着无效表单反复重试。
- 前端校验两次密码一致与长度下限，后端仍会独立校验一次。
- 成功后展示后端返回的「密码已重置，请使用新密码登录」并提供前往登录页的链接。

### 路由守卫

[`src/router/index.ts`](src/router/index.ts) 中的 `beforeEach` 按 `meta.requiresAuth` / `meta.requiresAdmin` 拦截：

- 未登录访问受保护路由（`/`、`/settings`、`/admin/*`）→ 重定向到 `/login`，并带上 `redirect` 查询参数，登录成功后跳回来源页；
- 已登录但非管理员访问 `/admin/users` → 重定向回首页；
- 已登录访问 `/login` → 直接跳回首页。

`/openapi` 与 `/reset-password` 不依赖登录态，保持公开。

注意 `/openapi` 的两层是分开的：**菜单入口**由 `menu.ts` 的 `adminOnly: true` 收敛为仅管理员可见，**路由**未加守卫、直达地址仍对任何访客开放。若日后要真正限制访问，应给该路由补 `meta: { requiresAuth: true, requiresAdmin: true }`（与 `/admin/*` 一致）。

## 与后端联调

后端工程位于 [`../api`](../api)，开发端口 **5004**，其开发环境已放行来自 `http://localhost:5173` 的 CORS 请求，因此本地可直接跨端口调用。

本工程**未使用 Vite proxy**：后端基址由 `public/conf/setting.json` 的 `api.baseUrl` 在运行时提供（见「运行时配置」），请求由浏览器直接发往该地址，因此**依赖后端放行的 CORS**。若前端端口发生变化，需同步调整后端 [`ConfigConst.FRONTEND_DEV_ORIGIN`](../api/Config/ConfigConst.cs)。

业务接口统一经 [`src/api/http.ts`](src/api/http.ts) 发起（自动附加令牌、统一错误文案与 401 处理），OpenAPI 调试页仍使用 [`src/api/openapi/`](src/api/openapi/) 下的独立实现。

后端可用的探针、认证与示例接口：

```
GET  http://localhost:5004/health                  # 存活探针
GET  http://localhost:5004/health/db               # 数据库连通性探针（返回当前库类型）
GET  http://localhost:5004/openapi/v1.json         # OpenAPI 文档（仅开发环境）

POST http://localhost:5004/api/auth/register       # 注册（201，不返回令牌，需管理员激活）
POST http://localhost:5004/api/auth/login          # 登录（200，返回令牌）
GET  http://localhost:5004/api/auth/me             # 当前用户（需 Bearer 令牌）
POST http://localhost:5004/api/auth/change-password # 自助修改密码（需 Bearer 令牌 + 原密码）
POST http://localhost:5004/api/auth/reset-password # 凭用户名 + 令牌设置新密码（免登录）

GET    http://localhost:5004/api/admin/users                    # 用户列表（需管理员）
POST   http://localhost:5004/api/admin/users/{id}/activate      # 激活
POST   http://localhost:5004/api/admin/users/{id}/deactivate    # 停用
POST   http://localhost:5004/api/admin/users/{id}/reset-link    # 生成 15 分钟一次性重置链接
DELETE http://localhost:5004/api/admin/users/{id}               # 删除
```

首次启动会自动播种默认管理员 `admin` / `admin123`（可用 `HAMSTER_ADMIN_USERNAME` / `HAMSTER_ADMIN_PASSWORD` 覆盖，详见[根 README](../README.zh-CN.md)）。
