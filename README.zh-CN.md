## 简介

Hamster 是一个全栈个人记账助手，旨在帮助您轻松管理财务。该项目采用 Vue 3 和 TypeScript 构建现代化、响应式的前端界面，后端使用高性能的 ASP.NET Core API。

## 项目结构

```
Hamster/
├── api/     # ASP.NET Core 后端（.NET 10 + Minimal API）
├── ui/      # Vue 3 前端（TypeScript + Vite）
└── doc/     # Logo 与图标资源
```

## 技术栈

### 后端 ([api/](api/))
- **框架**: ASP.NET Core 10.0（.NET 10）
- **API 风格**: Minimal APIs，端点模块通过 `IEndpoint` 约定自动注册
- **OpenAPI**: 开发环境通过 `AddOpenApi()` / `MapOpenApi()` 暴露文档（`/openapi/v1.json`）
- **数据访问**: SqlSugar ORM，支持 **SQLite**（默认）与 **PostgreSQL**
- **认证**: JWT 令牌（有效期 1 天），密码以 PBKDF2 哈希存储
- **分层**: `Config/` · `Data/` · `Security/` · `Services/` · `Endpoints/`

### 前端 ([ui/](ui/))
- **框架**: Vue 3.5 使用组合式 API（Composition API）
- **语言**: TypeScript 6.0
- **构建工具**: Vite 8
- **状态管理**: Pinia 4
- **路由**: Vue Router 5
- **代码检查 / 格式化**: ESLint + oxlint + Prettier
- **包管理器**: pnpm

## 快速开始

### 后端设置

```bash
cd api

# 运行开发服务器（默认 SQLite，无需任何准备）
dotnet run

# 构建项目
dotnet build

# 发布生产版本
dotnet publish -c Release
```

后端 API 默认运行在 `http://localhost:5004`。启动时会输出数据库类型、连接串（已脱敏）、
SQLite 文件路径与 JWT 签名密钥，便于确认实际生效的配置。

#### 数据库

默认使用 SQLite，开箱即用——首次启动时会在**当前执行目录**下创建 `hamster.db`，
并通过 SqlSugar CodeFirst 自动建表。

```bash
# 改用 PostgreSQL（连接串与默认值一致时可省略）
export HAMSTER_DB_TYPE=PostgreSql
export HAMSTER_DB_CONNECTION="Host=localhost;Port=5432;Database=hamster;Username=postgres;Password=postgres"
```

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `HAMSTER_DB_TYPE` | `Sqlite` | 取值为 `Sqlite` 或 `PostgreSql` |
| `HAMSTER_DB_CONNECTION` | *（空）* | 连接串；留空时按数据库类型生成默认连接串 |
| `HAMSTER_DB_AUTOMIGRATE` | `true` | 启动时是否执行 CodeFirst 建表 |

环境变量优先级始终高于 `appsettings.json`。自动建表失败（如数据库连不上）时仅记录告警，
不会阻断应用启动。

健康探针：`GET /health`（存活探针，不访问数据库）与 `GET /health/db`（数据库连通性，
不可用时返回 `503`）。

#### 认证

登录使用 JWT 令牌，有效期**固定 1 天**；密码以 PBKDF2（HMAC-SHA256）哈希 + 每用户随机盐存储。

```bash
# 可选：固定签名密钥（不设置时每次启动随机生成）
export HAMSTER_JWT_KEY="<至少 32 字节的随机数据>"
```

未配置 `HAMSTER_JWT_KEY` 时会随机生成密钥并打印到控制台，**进程重启后此前签发的令牌将全部失效**，
长期部署请显式设置该变量。

##### 默认管理员

首次启动会自动播种一个系统管理员，使全新拉取的工程开箱可用：

> [!WARNING]
> 默认口令 **`admin` / `admin123` 仅用于开箱体验**。在把实例开放给他人之前，请先通过下面的
> 环境变量覆盖，或登录后立即改密。播种**只会创建**缺失的 `admin` 账号，**绝不覆盖已有密码**，
> 因此改过一次即不会再被默认值还原。

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `HAMSTER_ADMIN_SEED_ENABLED` | `true` | 启动时是否播种默认管理员 |
| `HAMSTER_ADMIN_USERNAME` | `admin` | 播种的管理员用户名 |
| `HAMSTER_ADMIN_PASSWORD` | `admin123` | 播种的管理员密码（仅在创建账号时使用） |
| `HAMSTER_PUBLIC_BASE_URL` | `http://localhost:5173` | 拼接密码重置链接所用的前端地址 |

##### 账号生命周期

1. **注册**：`POST /api/auth/register` 创建的账号默认**未激活**，且**不签发令牌**。
2. **激活**：由管理员在用户管理页 `/admin/users` 激活；在此之前登录一律返回 `403` 与「账号尚未激活，请联系管理员激活」。
3. **登录**：`POST /api/auth/login` 返回令牌。停用账号会阻止后续登录；**已签发的令牌在过期前仍然有效**（有效期 1 天）。
4. **重置密码**：管理员生成**有效期 15 分钟、一次性**的重置链接（`POST /api/admin/users/{id}/reset-link`）并交付用户。链接打开 `/reset-password?username=…&token=…`，需**同时**提供用户名与令牌；服务端只存令牌的 SHA-256 哈希，用后立即清空。所有失败原因统一返回同一 `400` 文案，避免被用于探测用户名。
5. **删除**：`DELETE /api/admin/users/{id}` 删除账号并**立即使其令牌失效**。

管理员不可停用或删除自己的账号。管理员身份**不写入 JWT**：每个管理端点都回查数据库，
因此撤销权限立即生效。登录同样遵循**先验密码、后判激活**的顺序——密码错误先返回 `401`，
匿名请求无法借此得知「某用户名存在但未激活」。

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/auth/register` | — | 注册（201，**不返回令牌**）；用户名已存在返回 409 |
| `POST /api/auth/login` | — | 登录（200，返回令牌）；凭据错误返回 401，账号未激活返回 403 |
| `GET /api/auth/me` | Bearer | 当前登录用户 |
| `POST /api/auth/reset-password` | — | 凭 `{ username, token, newPassword }` 设置新密码；链接无效、已过期或已使用统一返回 400 |
| `GET /api/admin/users` | 管理员 | 用户列表 |
| `POST /api/admin/users/{id}/activate` | 管理员 | 激活用户（204） |
| `POST /api/admin/users/{id}/deactivate` | 管理员 | 停用用户（204）；停用自己返回 400 |
| `POST /api/admin/users/{id}/reset-link` | 管理员 | 生成 15 分钟一次性重置链接 |
| `DELETE /api/admin/users/{id}` | 管理员 | 删除用户（204）；删除自己返回 400 |

##### 账套

**账套**是一组业务数据的归属单位（如「家庭」与「公司」）。账套与用户是**多对多**关系：管理员在
`/admin/account-sets` 把用户关联到账套。管理员自身无需关联——可查看并切换到**全部**账套。

普通用户登录后的行为取决于其可访问的账套数量：

| 可访问账套数 | 登录后 |
|---|---|
| 0 个 | header 显示「暂无可用账套」，不显示账套名称与切换按钮 |
| 1 个 | 自动选中，不打扰用户 |
| 2 个及以上 | **先弹出选择弹窗**，未选定前无法关闭（弹窗内提供「退出登录」作为逃生入口） |

选定后，header 会在**退出登录之前**显示当前账套名称与【切换】按钮。

当前账套随每个请求以 `X-Account-Set-Id` 请求头携带，并由后端**逐请求**校验用户与该账套的关联关系
——账套刻意**不写入 JWT**：写进令牌后，管理员调整关联关系须等令牌过期（1 天）才对用户生效，
逐请求校验则在**下一次请求**即生效。

账户表 `hamster_account` 是**首张真正按账套隔离**的业务表（见下节）；示例表 `sample_account`
仍无账套字段。新增业务表请沿用同一约定：加 `account_set_id` 列，并以
`CurrentAccountSetExtensions.ResolveCurrentAccountSetAsync`（依请求头解析并鉴权账套）解析当前账套，
**未解析到账套即拒绝请求**——否则会退化成「查询全库数据」。

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/account-sets/mine` | Bearer | 我可访问的账套（管理员为全部） |
| `GET /api/account-sets/current` | Bearer | 依 `X-Account-Set-Id` 解析当前账套：不带头返回 `null`，格式非法返回 400，账套不存在或无权访问返回 403 |
| `GET /api/admin/account-sets` | 管理员 | 账套列表（含关联用户数） |
| `POST /api/admin/account-sets` | 管理员 | 新建账套（201）；名称重复返回 409 |
| `PUT /api/admin/account-sets/{id}` | 管理员 | 修改名称与备注（204） |
| `DELETE /api/admin/account-sets/{id}` | 管理员 | 删除账套并清除其关联（204） |
| `GET /api/admin/account-sets/{id}/members` | 管理员 | 账套关联用户 Id 列表 |
| `PUT /api/admin/account-sets/{id}/members` | 管理员 | 以 `{ userIds }` **整体替换**关联用户（204） |

##### 账户

**账户**是记账业务中资金与债务的挂靠对象，归属且仅归属一个账套：账户列表按当前账套过滤，
切换账套即切换账户集合（`hamster_account` 是第一张真正按账套隔离的业务表）。

归属范围分两种，可见性由后端逐请求判定：

| 归属范围 | 谁能看见、谁能改 |
|---|---|
| 公共账户 | 账套内**全部成员**，用于家庭共用的账户 |
| 个人账户 | **仅归属人本人**（归属人 = 创建者，创建后不可转让） |

系统管理员是唯一例外：对任意存在的账套均可访问（仍须带账套请求头），且可见并可改账套内的
**全部**账户（含他人个人账户）。本任务中「可见集合 = 可改集合」，故没有「只读可见」这一态。

账户类型固定四类，不支持用户自定义：

| 类型 | 取值 | 说明 | 用户可选 |
|---|---|---|---|
| 账本账户 | `Ledger` | 记账用的汇总性账户，本身不代表具体的钱 | **否**——由系统自动创建，且不在账户列表中呈现 |
| 资金账户 | `Fund` | 实实在在的钱（现金、银行卡、电子钱包等） | 是 |
| 负债账户 | `Liability` | 欠别人的钱（信用卡、借款等），期初金额允许为负 | 是 |
| 往来账户 | `Contact` | 人情往来与应收应付（借出、借入、待收报销等） | 是 |

账户类型还有一条**使用侧**的规则：可作为**转账**转出/转入的只有**资金账户与负债账户**，
由 `AccountTypeExtensions.IsTransferAccount` 一处判定（与 `IsUserAssignable` 同构），
转账端点的校验与错误文案都从它派生。往来账户记录的是「谁欠谁」而不是「钱放在哪」，
钱转进转出它并不改变钱的所在；账本账户则是系统内部账户——两者都不作转账的端点。
这不是新增账户类型，只是「哪几类账户之间可以转账」的规则。

**账本账户是纯系统内部账户**：它只作期初余额入账的复式对手方，**不接受手工建立**
（`POST` 传 `type: "Ledger"` 一律 400），也**不在任何账户列表中呈现**——
管理员的列表同样不含它。不做例外、不设开关，可见性口径唯一。
它照常计入余额与参与复式配平，隐藏的只是界面呈现。是否可由用户指定由
`AccountTypeExtensions.IsUserAssignable` 一处判定，端点的校验与错误文案都从它派生；
该判定**只服务新建路径**——账户类型一经创建即不可修改（见下表 `PUT` 行），
故「把既有账户改成账本账户」这条绕路随类型不可改一起消失。

**期初金额**是账户建立时已有的金额（两位小数以内），创建时即落成一笔期初交易（详见下节），
**创建后不可修改**——调整余额应记一笔余额调整交易，而不是改写既成的期初。
**余额**是**只读派生值**，等于该账户全部交易明细的有符号汇总。数据库中**没有余额列**：
派生值只留一条计算路径，避免「余额列忘了同步」的静默错账。

账户**不做物理删除**，只有停用/启用（软删除）：账户是流水的挂靠对象，物理删除会让历史流水悬空。
停用后默认不出现在列表中，加 `includeInactive=true` 可查看并重新启用。

`isSystem` 标记系统自动创建的账户（当前即期初账本账户）。它**不接受用户创建，也不出现在账户列表中**
（列表过滤依据是类型 `Ledger`，见上表；「不在列表中」与「不可手工建立」互为闭环）。
`isSystem` 本身只用于「按需创建时复用同一条」，身份记在标记列上，不靠名称或类型反查——
而名称与类型本就都不是可改项（见下表的 `PUT` 行），故不存在任何能让系统认不出自己这条账户的途径。

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/accounts?includeInactive=false` | Bearer | 当前账套内我可见的账户（管理员为全部），`balance` 为派生余额；**不含账本账户** |
| `POST /api/accounts` | Bearer | 新建（201）；请求体 `{ name, scope, type, initialBalance, currencyCode }`，`type` 只能是 `Fund` / `Liability` / `Contact`；`currencyCode` 须为**启用的**币种且创建后不可修改；个人账户的归属人强制为当前登录者；期初金额非 0 时同时落成一笔期初交易 |
| `PUT /api/accounts/{id}` | Bearer | 只修改名称（204），请求体仅 `{ name }`；归属范围、归属人、所属账套、**账户类型**、**币种**与**期初金额**一经创建均不可修改。请求里带上 `type` 也不会被读取 |
| `POST /api/accounts/{id}/deactivate` | Bearer | 停用（软删除，204） |
| `POST /api/accounts/{id}/activate` | Bearer | 启用（204） |

失败约定：未携带账套请求头返回 400（账户一律挂在账套下）；账套不存在或无权访问返回 403；
账户不存在、不属于该账套或对当前用户不可见一律返回 **404**（三种情形同响应，避免被用于探测）；
名称在「账套 + 归属范围」内重复返回 409。`scope` / `type` 对外为**字符串**，
传数字或未知名称一律 400。

##### 分类

**分类**回答的是「这笔账因何而发生」（餐饮、工资、还信用卡等），归属且仅归属一个账套：
分类列表按当前账套过滤，与账户同一口径，故每个账套各有一份自己的词汇——
「餐饮」在两个账套里覆盖的范围可以完全不同。

分类**刻意不拆「用户侧 / 管理侧」**（这一点与币种相反）：分类是账套内所有成员共用的字典，
维护它不需要系统管理员身份；拆出去只会让普通用户面对一个自己建的分类却无权改名。

分类**不区分收入 / 支出 / 转账**：分类是「钱花在什么事上」，而资金流向已由交易的 `type` 承载。
给分类绑上类型，会逼着同一个名字按类型各建一份，且「购物退款」这类在收入与支出上同属一个分类的
场景将无法记录。同理，**`GET` / `POST` 端点里没有类型参数**——本就没有这个维度可筛。

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/categories?includeInactive=false` | Bearer | 当前账套内的分类，按创建顺序正序；`includeInactive=true` 一并返回已停用的分类 |
| `POST /api/categories` | Bearer | 新建（201）；请求体 `{ name }`，32 位以内 |
| `PUT /api/categories/{id}` | Bearer | 仅改名（204）——请求体只有 `{ name }`；账套不可改，且**不在请求记录上**，传了也不会被读取 |
| `POST /api/categories/{id}/deactivate` | Bearer | 停用（软删除，204） |
| `POST /api/categories/{id}/activate` | Bearer | 启用（204） |

错误契约：未带账套请求头 400（分类恒挂在某个账套内）、`name` 不合法 400；账套不存在或无权 403；
分类不存在或属于其他账套 404；同一账套内重名 409。名称比对**去空白后不区分大小写**，
故「餐饮」与「 餐饮 」是同一个名字，不会并存两份。

分类**不做物理删除**，只有停用/启用（软删除），理由与账户相同：交易挂在它上面，物理删除会让历史流水悬空。
停用后默认不出现在列表中，记账时**也不再作为候选**；但明细查询**照常返回它的名称**——历史必须能读通。

**分类挂在交易头上，而非明细上**（见 `hamster_transaction.category_id`）：它描述的是「这笔账因何而发生」，
是记账这一行为本身的属性。一笔转账会落借贷两条明细，若分类挂在明细上，一笔转账就要选两个分类——
而转账的分类（如「还信用卡」）天然是整笔的。由此带来一个需要知道的结果：
**同一笔交易的两条明细携带同一个分类**。

存**主键**而非分类名，是改名安全的前提：历史明细始终指向同一行，故改名后自动显示新名称，
不会让同一个分类在账面上裂成两个。

**分类刻意不播种、也不回填。** 播种等于先替各账套编一套词汇再让用户去删，且它实质上不幂等——
用户删掉的分类会在下次启动被塞回来，管理页自己的改动形同虚设（币种不同，「所有人都需要的那几个」
确有其共识，故 `CurrencySeeder` 成立）。空字典 + **记账时手工输入自动创建**，正好覆盖「开箱可用」。
`category_id` 同理不必回填：它是可空 `int`，既有行取到 NULL 正是「未分类」这一合法值。

##### 交易与流水

记账采用**复式记账**：**每一笔交易都有借贷两条明细**，借方金额合计恒等于贷方金额合计。
数据分两张表：

| 表 | 内容 |
|---|---|
| `hamster_transaction` | 交易头：账套、类型、发生时间、摘要、备注、**分类**、记账人 |
| `hamster_transaction_entry` | 交易明细：所属交易、账户、借贷方向、金额 |

明细的方向用 **`direction` 枚举 + 正数金额**表示，而不是「金额带正负号」：

| 方向 | 取值 | 对该账户余额 |
|---|---|---|
| 借方 | `Debit`（1） | 增加 |
| 贷方 | `Credit`（2） | 减少 |

符号换算**只有一个定义**（`EntryDirectionExtensions.SignedAmount`：借方计正、贷方计负），
由两处共用——账户余额汇总（`SumSignedAmountsAsync`）与明细出参的 `signedAmount` 字段；
其余各处一律只搬运正数金额。刻意**不按账户类型翻转符号**（例如「负债账户贷方表示增加」）——
那会让同一个 `direction` 在不同账户上含义相反，符号一旦分散到多处就再难对齐。

借贷配平由**写入侧保证**：每条明细都是「目标账户 + 对手方账户」成对写入，
没有只写单边的入口。

交易头的 `type` 有四种取值，**四种都有真实的写入路径**（不留只占位的枚举值）：

| 类型 | 取值 | 产生方式 | 方向（目标账户 / 对手方） |
|---|---|---|---|
| 期初余额 | `OpeningBalance`（1） | 建账户（或升级回填）时系统自动生成 | 借方 / 贷方（期初金额为负时自动翻转） |
| 收入 | `Income`（2） | 用户在「收入」页手工记账 | **借方**（余额增加）/ 贷方 |
| 支出 | `Expense`（3） | 用户在「支出」页手工记账 | **贷方**（余额减少）/ 借方 |
| 转账 | `Transfer`（4） | 用户在「转账」页手工记账 | **贷方**（转出账户余额减少）/ 借方（转入账户余额增加） |

方向由**交易类型**决定而非金额符号：金额恒为正，两条明细等额反向，配平天然成立。
**转账与支出同向**——转出账户就是「钱离开的那个账户」，记贷方；转入账户作为对手方记借方。
「哪些类型可由用户手工记账」由 `TransactionTypeExtensions.IsUserRecordable` 一处判定
（与账户类型的 `IsUserAssignable` 同构），端点的校验与错误文案都从它派生——
期初余额只能由系统生成，手工传 `OpeningBalance` 一律 400；其余三种共用同一个记账端点。

###### 期初余额

建账户时，期初金额**自动落成一笔期初交易**，而不是只写进 `initial_balance` 列：

```
期初金额 500 的「现金」：
  借  现金      500
  贷  期初账本  500
```

**期初账本账户**（名称「期初账本」，类型 `Ledger`，公共归属，`isSystem = true`）是这笔交易的对手方，
由系统**按需自动创建**：账套内首次需要时创建，之后复用，**一个账套恒只有一个**。
它**不呈现于账户列表**，也不接受手工建立（见上文「账户」一节的类型表：新建传 `Ledger` 一律 400；
而既有账户的类型如今根本不可修改，故连「先建别的类型再改过来」这条绕路也不存在）。
期初金额为 0 的账户**不写任何分录**（其明细汇总恒为 0，与期初金额一致）；
期初金额为负的账户（负债）方向自动翻转——目标账户落贷方（余额减少），账本账户落借方。

于是**余额 = 全部明细的有符号汇总**，期初分录本身就是「+期初金额」，故**不再叠加 `initial_balance`**，
否则期初金额会被重复计一次。

既有账户（本次升级前已存在）在启动时由**期初余额回填**补写缺失的期初交易：幂等，
已含期初分录的账户不受影响，回填写入的交易不带记账人；失败只告警，不阻断启动。

**账本账户是期初余额、收入、支出共同的对手方**：系统按账套按需创建，首次需要时建、之后复用，
三种记账都落在同一个账户上，故一个账套恒只有一个。**转账是唯一的例外**——它的对手方是
另一个真实账户（转入账户），账本账户完全不参与，故转账不写账本账户的分录。
它也**不是**「期初专用」，
名称里的「期初」二字只记录了它诞生于期初入账这一历史——它从不出现在任何界面上，改名与否不影响使用。

###### 记一笔收入、支出与转账

三种记账**共用同一个写入端点**，不提供单笔交易查询：

| 端点 | 认证 | 说明 |
|---|---|---|
| `POST /api/transactions` | Bearer | 记一笔收入、支出或转账（201）。请求体 `{ type, accountId, amount, occurredAt, summary, remark, currencyCode, counterpartyAccountId, counterpartyName, categoryId, categoryName }`：`type` 只能是 `Income` / `Expense` / `Transfer`（字符串，传数字或 `OpeningBalance` 一律 400）；`amount` 须 `> 0` 且至多两位小数；`occurredAt` 为 ISO 8601 时间，取**业务发生时间**（可补记往日）；`summary` 必填（≤128）、`remark` 可选（≤256）；`currencyCode` 必填且**须与两个账户的币种一致**；`counterpartyAccountId` 与 `counterpartyName` 两者皆空即「未指定对手方」，同时给出时**以主键为准**（主键比名称精确）；`categoryId` 与 `categoryName` 两者皆空即「未分类」。返回落库后的交易（含 `id` / `accountName` / `counterpartyName` / `categoryName`） |

该端点同时落成两条明细、金额相等方向相反，方向由 `type` 推出（见上表），故 `amount` 恒为正。
`accountId` 是**目标账户**：收入时是收入账户（余额增加），支出时是支出账户、**转账时是转出账户**
（两者余额均减少）。对手方的来源分四种：

| 对手方 | 触发条件 | 语义 |
|---|---|---|
| 按主键指定 | `counterpartyAccountId` 给出一个可见账户主键 | 一笔**两个真实账户之间**的资金转移 |
| 按名命中 | `counterpartyName` 命中一个既有的可见账户 | 同上——名称只用来查找，不会因此新建 |
| 按名新建 | `counterpartyName` 查不到任何可见账户 | 自动创建为个人**往来账户**（期初 0，故不写期初分录），再按前两条处理 |
| 系统账本账户 | 两者皆空 | 「款项来自/去往账套之外」 |

**分类是可选的**，来源分三种，解析规则同「主键优先，否则按名」：

| 分类 | 触发条件 | 语义 |
|---|---|---|
| 按主键指定 | `categoryId` 给出当前账套内的一个分类主键 | 按指定挂上 |
| 按名命中 | `categoryName` 命中**当前账套内**的一个分类，**含已停用的** | 同上——名称只用来查找，不会因此新建 |
| 按名新建 | `categoryName` 查不到任何分类 | 在当前账套内**自动创建**该分类并挂上 |
| 无 | 两者皆空 | 「未分类」——合法状态，不是缺值 |

按名命中**连已停用的分类也算命中**：用户一字不差地打出这个名字，说明要的就是**那一个**；
若另建一个同名的启用分类放在它旁边，停用行上挂着的历史就会被劈成两半。分类与对手方的差别在于，
这里的按需新建**正是本功能的目的**（记账人输入一个新分类名，本就期待它被建出来），且它
**对三种记账类型都成立、含转账**——对手方的按名新建则不允许转账走：按名新建出来的是**往来账户**，
放行会让转账的对手方绕开「只允许资金/负债」的限制；分类没有这类限制可绕。

分类的解析**放在所有校验闸门之后**：解析可能真的建出一行分类，故一个注定被拒的请求
不应在分类表里留下痕迹。

**一笔转账只带一个分类、不是两个**——分类挂在交易头上，两条明细共用它。

**转账只走第一支**：它的两个端点都是真实账户，没有「账套之外」这一说，故除 `type` 外只多四条专有校验
（其余字段规则与收支完全共用）：

| 校验 | 触发条件 | 响应 |
|---|---|---|
| 转入账户必填 | `counterpartyAccountId` 为空 | 400 |
| 不接受按名新建 | `counterpartyName` 非空 | 400 |
| 两端必须都是**资金账户或负债账户** | `accountId` 或 `counterpartyAccountId` 指向的账户类型不满足 `AccountTypeExtensions.IsTransferAccount`（即 `Fund` / `Liability`） | 400，文案带上账户名与它的实际类型 |
| 两端不得是同一个账户 | `counterpartyAccountId` 与 `accountId` 相同 | 400 |

第二条不是可有可无的洁癖：按名新建出来的是**往来账户**，若放行（或只是忽略该字段），
转账的对手方就会绕开「只允许资金/负债」这条限制。

错误契约：未选账套 400；`type` / `amount` / `occurredAt` / 文本不合法 400；
**两个账户币种不一致**（含 `currencyCode` 与账户对不上）返回 400；转账的上述四条专有校验返回 400；
`categoryId` **在当前账套内不存在**亦返回 400（落在 `categoryId` 字段上，**不是 404**，理由见下）；
**账户不可见、不存在或属于其他账套一律 404**（三种情形回答相同，避免被用来探测他人账户）；

分类的失败码**刻意与账户不一致**：账户解析不到回 404，是为了不让端点被用来探测他人账户；
而分类**没有可见性维度可挡**——账套内每个分类对每个成员都可见（这正是上面不拆用户侧/管理侧的结果），
404 在这里保护不了任何东西，400 则是更好的答案：它是请求体字段级错误，会与其余字段错误**一并聚合**返回，
而不是抢先短路，于是一次请求可以同时报出「金额不合法**且**分类不合法」。
当前账套的**系统账本账户本身不可记**——它不出现在任何账户列表里，故请求方拿不到它的主键。

需要逐条明细（含对手方档位与带符号金额）请用 `GET /api/entries`：
为「读回刚刚写入的那笔」再开一个近似端点，只会多出一条会与明细查询漂移的读取路径。

###### 账目明细查询

明细统一由一个端点读回，回答「哪笔钱、什么时候、动在哪个账户」：

| 端点 | 认证 | 说明 |
|---|---|---|
| `GET /api/entries?from=&to=&accountIds=&page=&pageSize=` | Bearer | 当前账套内的交易明细，按发生时间正序分页；`from` / `to` 为 ISO 8601 时间、与交易的**业务发生时间**（`occurred_at`）比较且**均为闭区间**，省略即该侧不限；`accountIds` 可重复传参、也可整体省略；`page` 默认 1，`pageSize` 默认 50（上限 **200**）。返回 `{ items, total, page, pageSize }` |

**一行是一条明细，不是一笔交易。** 一笔交易由借贷两条明细构成，当两侧都落在所选账户上时就会呈现
两行。`amount` **恒为正**、`direction`（`Debit` / `Credit`）为借贷方向，两者是账本的底层事实
（库内不存带符号金额）。

**呈现请用 `signedAmount`**：它是 `amount` 按 `direction` 取符号后的值（借方为正、贷方为负），
含义是「该条明细对它挂靠账户的余额增减」。界面的收入/支出分列与正负着色都由它派生，
调用方因此**不必**自己再做一次方向→符号的折算——换算的定义只有一处
（`EntryDirectionExtensions.SignedAmount`），与账户余额汇总 `SumSignedAmountsAsync` 共用。

排序为 `occurred_at` 升序 → 交易主键 → 明细主键。第三级排序键不是装饰：缺了它，同一时刻的行可能在
两次请求间互换位置，同一行会在两页里各出现一次。

**可见性不在这里另写一份。** 可见账户集来自既有的
`IAccountService.ListByAccountSetAsync(..., includeInactive: true, ...)`——与账户列表同一个唯一来源——
明细再以之过滤。`includeInactive: true` 是必须的：账户是软删除，停用账户上仍挂着历史明细，
漏掉它会让过去的账凭空消失，而数据其实还在库里。本功能对 `IAccountService` 与 `ITransactionService`
**零改动**，期初入账、余额汇总与回填链路完全不受影响。

`accountIds` 与可见集合**求交**而非校验：看不见的主键被静默剔除（不报错、也不返回其明细），
交集为空则返回空页。若对不可见账户回 403/404，这个参数就成了探测他人账户的探针。

对手方定义为同一交易中方向相反的那条明细，以**分档**的 `counterpartyKind` 对外：

| `counterpartyKind` | 含义 | 携带信息 |
|---|---|---|
| `Account` | 对手方对调用者可见 | `counterpartyAccountId` + `counterpartyName` |
| `Ledger` | 对手方是期初**账本账户** | 无——不给主键、不给名称 |
| `Hidden` | 对手方存在但对调用者不可见 | 无——不给主键、不给名称 |
| `None` | 该交易里没有反向明细 | 无 |

把 `Ledger` 从 `Hidden` 里单独分出并不构成信息披露：账本账户是系统自有账户、每账套恰有一个、
其存在性本文档已经写明，且它从不出现在任何账户列表里。他人的个人账户则连主键都不给。

**一笔转账在这里呈现为两行**：转出账户记贷方（落支出列）、转入账户记借方（落收入列），
两条的 `counterpartyKind` 均为 `Account`——转账的两端都是真实账户，没有账本账户参与。
两行的形状与「一笔支出 + 一笔收入」完全相同，**交易类型标签是唯一的区分线索**，
故它旁边会显示「转账」；两行照常各自计入「本页小计」，不做合并也不排除。

每行同时携带 `categoryId` + `categoryName`。**两者没有档位之分**——与对手方不同，分类没有需要遮的东西：
账套内每个分类对每个成员都可见。交易**未分类**时两者均为 `null`，那是正常状态而非缺值。
**名称由后端给出**，而不是反范式化写到交易行上，故改名会自动反映到历史明细上
（写死名称会让旧明细停在旧名字上，同一个分类在账面上裂成两个）。**已停用**分类的名称照常返回：
那些账确实发生过，藏起标签只会让历史读不通。因为分类是交易级的，**同一笔交易的两条明细携带同一对值**——
转账的两行共用一个分类。

失败约定：未带账套请求头 400（「请先选择账套」）；账套不存在或无权 403；用户查不到 401；
`from` / `to` 格式非法、`from` 晚于 `to`、`page < 1`、`pageSize` 超出 `1..200` 一律 400 字段级错误。

##### 升级既有数据库

SqlSugar 的增量加列只会把新列补成**可空**，不会为既有行填值。因此启动时会先把历史用户行的
`is_admin` / `is_active` 回填为 `false`，即**本次升级前已注册的账号一律是「非管理员 + 未激活」**，
需由管理员在用户管理页激活后才能登录。同理，历史账户行的 `is_system` 回填为 `false`
（升级前的账户不可能是系统账户）；不补这一步，`is_system` 为 NULL 会让账户列表因无法绑定而 500。
